# 결정 기록하기

결정의 **결과는 코드와 문서에 남지만 이유는 아무 데도 남지 않는다.** 몇 주 뒤
같은 논의를 반복하거나 이미 버린 대안을 다시 검토하게 된다. 이 기록이 그걸
막는다.

제출물의 재료이기도 하다. 기획 결정은 게임 소개 문서로, AI 환경 결정은 AI 활용
기술 문서로 흘러간다.

## 1. 어느 축인지 정한다

| 결정 내용 | 기록 위치 |
| --- | --- |
| 무엇을 만들 것인가 — 게임 규칙, 컨텐츠, 밸런스 | `docs/game-design/decisions.md` |
| 게임을 어떻게 만들 것인가 — 엔진, 구조, 라이브러리, 에셋 정책 | `docs/tech-design/decisions.md` |
| Claude Code 로 어떻게 개발할 것인가 — 훅, 규칙, 스킬, 로깅 | `docs/ai/setup.md` |

IMPORTANT: 이 경계를 흐리지 않는다. 훅이나 규칙 설계는 게임 기술이 아니다.
판단이 서지 않으면 사용자에게 묻는다.

`docs/ai/setup.md` 는 형식이 다르다. 시간순 목록이 아니라 주제별 문서이므로,
"설계 판단" 절 아래에 소제목으로 추가한다.

## 2. 형식에 맞춰 쓴다

`decisions.md` 두 곳은 **새 항목을 맨 위에** 넣는다. 최근 결정이 먼저 보여야
한다.

```markdown
## YYYY-MM-DD · <결정을 한 줄로>

<왜 그렇게 정했는지. 무엇을 정했는지보다 판단 근거가 중요하다.>

버린 안: <검토했으나 택하지 않은 것과 그 이유>
```

## 3. 확인할 것

- **버린 안을 생략하지 않는다.** 검토한 대안이 없었다면 그렇게 적는다.
  이 줄이 나중에 "이건 왜 안 했지" 를 막아준다.
- **결과가 아니라 이유를 쓴다.** "URP 로 정했다" 가 아니라 "HDRP 는 WebGL 을
  지원하지 않아서" 다.
- 논의 중에 결론이 뒤집혔다면 **그 과정도 적는다.** 무엇이 판단을 바꿨는지가
  가장 값어치 있다.
- 결정에 따라 문서나 코드가 바뀌었다면 **같은 커밋**에 담는다.

## 쓰지 않는 것

- 아직 정해지지 않은 것. 검토 중인 사안은 기록하지 않는다
- 되돌릴 수 있는 사소한 선택. 변수명이나 폴더 이름 같은 것
- 이미 적힌 결정의 재탕. 바뀌었다면 새 항목으로 추가하고 이전 항목은 두어
  변경 이력이 남게 한다
