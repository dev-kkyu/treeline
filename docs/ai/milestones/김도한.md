# AI 활용 마일스톤 - 김도한

## 2026-08-08 · Unity·Blender MCP 파이프라인 R&D (작업은 8/4~8/5, 저장소 밖)

저장소 밖 별도 Unity 프로젝트(`TestGame`)에서 **AI가 게임 제작을 어디까지 끌고
갈 수 있는지** 실측했다. 프로토타입 생성 → 도구 연결 → 에셋 제작 → 엔진 반영까지
한 줄로 이어보는 것이 목적이었고, 자동 로그가 닿지 않는 곳이라 여기 남긴다.

**1단계 — 원샷 프로토타입 (성공).** "총게임 만들어줘" 한 마디로 웨이브 방식 1인칭
슈터가 나왔다. 런타임 스크립트 7개와 씬을 통째로 조립하는 에디터 스크립트까지
만들어 컴파일 오류 0으로 붙었고, 에디터 메뉴 한 번이면 아레나·표적·적 프리팹·HUD가
생성된다. 시키지 않았는데 걸림돌을 먼저 치워둔 점이 눈에 띄었다 — 적 추격을
CharacterController 직접 이동으로 짜서 NavMesh 베이크를 없앴고, TextMeshPro
Essential 임포트 없이도 돌아가게 레거시 `Text`를 썼고, 플레이어와 총을
`Ignore Raycast` 레이어로 빼 자기 총에 맞는 문제를 막았다. **요구가 한 갈래이고
규모가 작으면 원샷이 통한다**는 데이터다.

**2단계 — MCP 붙이기.** MCP for Unity(CoplayDev v10.1.0)와 blender-mcp(1.8.0)를
연결했다. `uv` 설치, `manifest.json`에 git URL 의존성 추가(백업 남김), Blender
애드온 배치 후 **헤드리스로 실제 로드 테스트를 거쳐** 프리퍼런스에 저장하는
순서로 진행했다. Unity는 8080(브리지 38000), Blender는 9876으로 붙었다.

여기서 세 가지를 배웠다.

- **문서보다 소스가 맞다.** 애드온 패널을 못 찾아 헤맸는데, README가 말하는
  "Connect to Claude" 버튼이 실제 코드에는 "Connect to MCP server"였다. 애드온의
  `draw()` 를 직접 읽어 패널 구성을 그려주고서야 찾았다.
- **MCP 서버는 세션 시작 시점에만 로드된다.** 세션 도중에 등록하면 그 세션에서는
  못 쓴다. 이걸 우회하려고 Blender에는 TCP 소켓으로, Unity에는 HTTP JSON-RPC로
  직접 명령을 쏘는 스크립트를 만들어 썼는데, 결과적으로 이 세션의 작업 대부분이
  그 경로로 돌아갔다. **MCP 도구 목록이 없어도 프로토콜만 알면 쓸 수 있다.**
- **외부 MCP 서버가 뭘 내보내는지 봐야 한다.** blender-mcp는 기동할 때마다
  제작자 Supabase로 사용 통계를 보낸다. 동의를 묻지 않고 기본으로 켜져 있고
  식별자가 파일에 저장돼 누적된다. 환경변수와 MCP 설정 양쪽에 차단을 걸고
  전송이 실제로 사라지는 것까지 확인했다.

**3단계 — MCP vs 헤드리스 스크립트.** 어느 쪽으로 모델링할지 물었더니 대립이
아니라고 답했다. blender-mcp의 핵심 도구가 Blender 안에서 Python을 실행하는
것이라 양쪽 다 결국 `bpy` 코드이고, 진짜 차이는 **살아있는 세션이냐 매번 새로 뜨는
배치냐**라는 것이었다. 결론은 형태를 탐색할 때는 MCP로 보면서 다듬고, 확정되면
헤드리스 스크립트로 옮겨 저장소에 남기는 방식. 실제로 적 로봇을 스크립트로
옮긴 뒤 헬퍼를 분리해 리팩터링했는데 같은 산출(3,384 tris)이 나오는 것까지
확인했다. 수치를 계속 만지게 되는 게임 에셋에서는 이 재현성이 크다.

**4단계 — 캐릭터 제작 → 리깅 → 애니메이션 → 엔진 반영.** 기존 적과 실루엣이
겹치지 않도록 어깨를 넓히고 머리를 낮춘 근접형 적을 만들어 FBX로 내보내고,
Unity에서 프리팹·머티리얼·씬 배치까지 자동으로 처리했다. 이어서 본 16개로 리깅해
Idle·Walk·Attack·Death 4종을 만들고, Animator 컨트롤러(Speed / Attack / Dead)를
코드로 생성한 뒤 기존 `EnemyAI`·`GameManager`를 고쳐 상태 전환과 스포너 혼합까지
연결했다. 스키닝은 자동 웨이트 대신 **부위별 강체 웨이트**(본 하나에 1.0)를 골랐다.
로우폴리 블록은 자동 웨이트로 붙이면 모서리가 뭉개져 늘어난다.

막혔다 푼 것들:

- **`Action.fcurves`가 없어졌다.** Blender 5.x가 레이어드 액션 체계로 바뀐 탓.
  호환 경로를 타게 우회했다. 이정범도 같은 함정을 밟았다 — **팀이 같은 벽에 두 번
  부딪혔다.**
- **긴 작업은 소켓 응답이 안 왔다.** export가 끝나도 응답이 돌아오지 않아 성공
  여부를 알 수 없었다. 결과를 로그 파일에 쓰게 바꿔 회수했다.
- **Unity `execute_code`의 제약 두 가지.** 안전 검사가 `AssetDatabase.DeleteAsset`을
  차단하고, 코드가 메서드 본문으로 실행돼 `using` 지시문을 못 넣는다. 타입을 전부
  정규화해서 넘겼다.
- **Avatar가 없어 T포즈가 될 뻔했다.** Generic 리그는 Avatar 없이 재생되지 않는데
  임포터의 `avatarSetup`이 `NoAvatar`였다. `CreateFromThisModel`로 바꿔 생성했다.
- **캡처가 거짓말을 했다.** 애니메이션 검증용 렌더가 프레임마다 똑같이 나와
  클립이 죽은 줄 알았는데, 실제로는 한 프레임 안에서 `cam.Render()`를 반복 호출하면
  SkinnedMeshRenderer가 갱신되지 않는 문제였다. 클립 커브 데이터를 직접 찍어보고,
  호출당 렌더 1회로 나눠서야 정상 포즈가 나왔다. **AI에게 눈으로 확인하라고 시킬
  때는 캡처 경로 자체를 먼저 의심해야 한다.**

**끝내 못 고친 것 — 적이 누워서 걸어온다.** 정지 상태에서는 멀쩡히 서 있는데
애니메이션이 돌면 눕는다. 원인까지는 잡았다. Blender Z-up ↔ Unity Y-up 보정으로
리그에 -90°, Root 본에 +90°가 들어가 서로 상쇄되는 구조였는데, `applyRootMotion`이
꺼져 있으면 Unity가 Root의 +90°를 버려서 -90°만 남는다. 정지 상태에서는 루트
모션이 돌지 않으니 드러나지 않았던 것이다. 그런데 고치는 쪽이 계속 어긋났다 —
`bake_space_transform`은 메시에만 먹고 아마추어에는 안 먹어 오히려 상쇄가 깨졌고,
unpack된 프리팹은 FBX를 재임포트해도 옛 복사본을 들고 있었다. 세 번 다른 방법으로
시도하다 중단했다.

**이 프로젝트에 남길 것.** 축 규약(up 축, 전방 축)은 파이프라인 **맨 앞에서 한 번
못 박고 그 뒤로는 손대지 않아야 한다.** 중간에서 보정하려 들면 상쇄 구조가 생기고,
그 구조는 정지 화면에서 정상으로 보여서 늦게 발견된다. 이정범 쪽에서도 전방 축을
반대로 잡아 걷기가 뒤로 가는 사고가 있었으니, **모델링 담당이 갈리기 전에 규약을
먼저 정해야 한다.**
