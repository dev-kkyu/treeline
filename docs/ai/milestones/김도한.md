# AI 활용 마일스톤 - 김도한

## 2026-08-08 · Unity·Blender MCP 파이프라인 R&D (작업은 8/4~8/5, 저장소 밖)

저장소 밖 별도 Unity 프로젝트(`TestGame`)에서 **AI가 게임 제작을 어디까지 끌고
갈 수 있는지** 실측했다. 프로토타입 생성 → 도구 연결 → 에셋 제작 → 엔진 반영까지
한 줄로 이어보는 것이 목적이었고, 자동 로그가 닿지 않는 곳이라 여기 남긴다.

**1단계 — 원샷 프로토타입 (성공).** "총게임 만들어줘" 한 마디로 웨이브 방식 1인칭
슈터가 나왔다. 런타임 스크립트 7개와 씬을 통째로 조립하는 에디터 스크립트까지
만들어 컴파일 오류 0으로 붙었고, 에디터 메뉴 한 번이면 아레나·표적·적 프리팹·HUD가
생성된다. 시키지 않았는데 걸림돌을 먼저 치워둔 점이 눈에 띄었다 — 적 추격을
CharacterController 직접 이동으로 짜서 NavMesh 베이크를 없앴고, TextMeshPro
Essential 임포트 없이도 돌아가게 레거시 `Text`를 썼고, 플레이어와 총을
`Ignore Raycast` 레이어로 빼 자기 총에 맞는 문제를 막았다. **요구가 한 갈래이고
규모가 작으면 원샷이 통한다**는 데이터다.

**2단계 — MCP 붙이기.** MCP for Unity(CoplayDev v10.1.0)와 blender-mcp(1.8.0)를
연결했다. `uv` 설치, `manifest.json`에 git URL 의존성 추가(백업 남김), Blender
애드온 배치 후 **헤드리스로 실제 로드 테스트를 거쳐** 프리퍼런스에 저장하는
순서로 진행했다. Unity는 8080(브리지 38000), Blender는 9876으로 붙었다.

여기서 세 가지를 배웠다.

- **문서보다 소스가 맞다.** 애드온 패널을 못 찾아 헤맸는데, README가 말하는
  "Connect to Claude" 버튼이 실제 코드에는 "Connect to MCP server"였다. 애드온의
  `draw()` 를 직접 읽어 패널 구성을 그려주고서야 찾았다.
- **MCP 서버는 세션 시작 시점에만 로드된다.** 세션 도중에 등록하면 그 세션에서는
  못 쓴다. 이걸 우회하려고 Blender에는 TCP 소켓으로, Unity에는 HTTP JSON-RPC로
  직접 명령을 쏘는 스크립트를 만들어 썼는데, 결과적으로 이 세션의 작업 대부분이
  그 경로로 돌아갔다. **MCP 도구 목록이 없어도 프로토콜만 알면 쓸 수 있다.**
- **외부 MCP 서버가 뭘 내보내는지 봐야 한다.** blender-mcp는 기동할 때마다
  제작자 Supabase로 사용 통계를 보낸다. 동의를 묻지 않고 기본으로 켜져 있고
  식별자가 파일에 저장돼 누적된다. 환경변수와 MCP 설정 양쪽에 차단을 걸고
  전송이 실제로 사라지는 것까지 확인했다.

**3단계 — MCP vs 헤드리스 스크립트.** 어느 쪽으로 모델링할지 물었더니 대립이
아니라고 답했다. blender-mcp의 핵심 도구가 Blender 안에서 Python을 실행하는
것이라 양쪽 다 결국 `bpy` 코드이고, 진짜 차이는 **살아있는 세션이냐 매번 새로 뜨는
배치냐**라는 것이었다. 결론은 형태를 탐색할 때는 MCP로 보면서 다듬고, 확정되면
헤드리스 스크립트로 옮겨 저장소에 남기는 방식. 실제로 적 로봇을 스크립트로
옮긴 뒤 헬퍼를 분리해 리팩터링했는데 같은 산출(3,384 tris)이 나오는 것까지
확인했다. 수치를 계속 만지게 되는 게임 에셋에서는 이 재현성이 크다.

**4단계 — 캐릭터 제작 → 리깅 → 애니메이션 → 엔진 반영.** 기존 적과 실루엣이
겹치지 않도록 어깨를 넓히고 머리를 낮춘 근접형 적을 만들어 FBX로 내보내고,
Unity에서 프리팹·머티리얼·씬 배치까지 자동으로 처리했다. 이어서 본 16개로 리깅해
Idle·Walk·Attack·Death 4종을 만들고, Animator 컨트롤러(Speed / Attack / Dead)를
코드로 생성한 뒤 기존 `EnemyAI`·`GameManager`를 고쳐 상태 전환과 스포너 혼합까지
연결했다. 스키닝은 자동 웨이트 대신 **부위별 강체 웨이트**(본 하나에 1.0)를 골랐다.
로우폴리 블록은 자동 웨이트로 붙이면 모서리가 뭉개져 늘어난다.

막혔다 푼 것들:

- **`Action.fcurves`가 없어졌다.** Blender 5.x가 레이어드 액션 체계로 바뀐 탓.
  호환 경로를 타게 우회했다. 이정범도 같은 함정을 밟았다 — **팀이 같은 벽에 두 번
  부딪혔다.**
- **긴 작업은 소켓 응답이 안 왔다.** export가 끝나도 응답이 돌아오지 않아 성공
  여부를 알 수 없었다. 결과를 로그 파일에 쓰게 바꿔 회수했다.
- **Unity `execute_code`의 제약 두 가지.** 안전 검사가 `AssetDatabase.DeleteAsset`을
  차단하고, 코드가 메서드 본문으로 실행돼 `using` 지시문을 못 넣는다. 타입을 전부
  정규화해서 넘겼다.
- **Avatar가 없어 T포즈가 될 뻔했다.** Generic 리그는 Avatar 없이 재생되지 않는데
  임포터의 `avatarSetup`이 `NoAvatar`였다. `CreateFromThisModel`로 바꿔 생성했다.
- **캡처가 거짓말을 했다.** 애니메이션 검증용 렌더가 프레임마다 똑같이 나와
  클립이 죽은 줄 알았는데, 실제로는 한 프레임 안에서 `cam.Render()`를 반복 호출하면
  SkinnedMeshRenderer가 갱신되지 않는 문제였다. 클립 커브 데이터를 직접 찍어보고,
  호출당 렌더 1회로 나눠서야 정상 포즈가 나왔다. **AI에게 눈으로 확인하라고 시킬
  때는 캡처 경로 자체를 먼저 의심해야 한다.**

**끝내 못 고친 것 — 적이 누워서 걸어온다.** 정지 상태에서는 멀쩡히 서 있는데
애니메이션이 돌면 눕는다. 원인까지는 잡았다. Blender Z-up ↔ Unity Y-up 보정으로
리그에 -90°, Root 본에 +90°가 들어가 서로 상쇄되는 구조였는데, `applyRootMotion`이
꺼져 있으면 Unity가 Root의 +90°를 버려서 -90°만 남는다. 정지 상태에서는 루트
모션이 돌지 않으니 드러나지 않았던 것이다. 그런데 고치는 쪽이 계속 어긋났다 —
`bake_space_transform`은 메시에만 먹고 아마추어에는 안 먹어 오히려 상쇄가 깨졌고,
unpack된 프리팹은 FBX를 재임포트해도 옛 복사본을 들고 있었다. 세 번 다른 방법으로
시도하다 중단했다.

**이 프로젝트에 남길 것.** 축 규약(up 축, 전방 축)은 파이프라인 **맨 앞에서 한 번
못 박고 그 뒤로는 손대지 않아야 한다.** 중간에서 보정하려 들면 상쇄 구조가 생기고,
그 구조는 정지 화면에서 정상으로 보여서 늦게 발견된다. 이정범 쪽에서도 전방 축을
반대로 잡아 걷기가 뒤로 가는 사고가 있었으니, **모델링 담당이 갈리기 전에 규약을
먼저 정해야 한다.**

## 2026-08-08 · B 담당 1단계 — Crawler 와 적 3종 모델링 시트

A·B·C 배정 후 첫 작업이다. 적 1종(`Crawler`)의 추격·공격·사망을 만들고, MeshyAI
에 넣기 전에 적 3종의 비율·실루엣·축 규약을 시트로 못 박았다.

**Crawler 는 플레이어 코드를 하나도 참조하지 않게 짰다.** 접점은 `Player` 태그 ·
`IDamageable` · `GameLayers.EnemySight` 셋뿐이고 전부 공용 계약이다. A 의
`Player.prefab` 이 오기 전에 태그만 붙인 캡슐로 검증을 시작할 수 있었고, 나중에
실제 프리팹으로 갈아끼웠을 때 고칠 것이 없었다. 서로 기다리지 않게 하려고 세운
인터페이스 규약이 실제로 값을 한 지점이다.

**에디터 작업을 전부 MCP 로 했다.** 프리팹 조립, NavMesh 베이크, 씬 구성, 플레이
모드 진입과 표본 수집까지. 사람에게 "에디터에서 이렇게 하세요" 로 넘긴 것은 없다.
Play 로 돌려 Crawler 가 8m 를 쫓아와 플레이어 체력 3칸을 0으로 만드는 것과,
반대로 두 대에 죽는 것까지 수치로 확인했다. 이정범의 `PlayerHealth` 를
`IDamageable` 로 때린 것이라 A·B 경계가 실제로 맞물리는 것도 함께 검증됐다.

가장 값어치 있는 건 **검증하다 잡은 두 가지**다.

- **`NavMeshSurface` 의 `layerMask` 기본값이 전부 포함이다.** 그대로 구우면 씬에
  놓인 플레이어와 적 캡슐이 걷는 면이 된다. 원점 샘플이 바닥이 아니라 캡슐
  윗면으로 잡히고 경로 계산이 실패하는데 **에러도 경고도 안 뜬다.**
- **구운 데이터를 씬에 묻으면 씬 파일 전체가 바이너리로 저장된다.** Force Text
  설정이어도 그렇다. 이건 잡은 게 아니라 **내가 저지르고 뒤늦게 발견한 것**이다.
  다시 열었을 때 오브젝트가 하나도 없어서 알았고, 0단계 커밋에서 씬을 복원한 뒤
  데이터를 별도 에셋으로 떼는 방식으로 다시 만들었다. git 이 `Bin 11413 ->
  47632 bytes` 로 이미 말해주고 있었는데 그때 안 봤다.

둘 다 레벨을 굽는 C 가 그대로 밟을 자리라 `architecture.md` 에 적었다.

**AI 에게 맡길 때의 함정도 네 개 모아 규칙으로 남겼다.** 특히 `execute_code` 의
컴파일러가 구버전이라 `in` 매개변수를 못 부른다. 공용 계약인
`IDamageable.TakeDamage(in DamageInfo)` 가 정확히 그 모양이라 셋 중 누구든
걸리는데, 컴파일 에러 문구만 봐서는 원인을 알 수 없다.

**되돌린 작업이 하나 있다.** `Resources.Load` 로 프리팹을 부르려고 폴더를 기능
기준으로 전면 개편했다가 원상복구했다. 아침에 임성규가 "한 폴더에 한 사람" 으로
병합 충돌을 막으려고 짠 구조를 반나절 만에 뒤집는 것이었고, 개편 없이도 담당
폴더마다 `Resources/` 를 두면 같은 목적을 달성할 수 있다는 걸 뒤늦게 확인했다.
푸시 전이라 커밋째 걷어냈다. **팀이 이미 합의한 구조를 바꿀 때는 대안을 먼저 다
따져보고 그 사람에게 말하는 것이 순서다.**

**모델링 시트 5장**(`docs/enemy-sheets/`)은 SVG 를 그려 헤드리스 Chrome 으로 굽는
파이썬 스크립트로 만들었다. 그림을 먼저 그린 이유는 기획의 검수 기준이 형태이기
때문이다 — 「역광에서 검은 실루엣만 보여도 셋이 구분되는지」. 글로 "낮고 빠르다 /
천장에 붙는다 / 크다" 라고 적어두면 생성 단계에서 셋이 서로 닮아가고, 리깅까지
간 뒤에는 되돌릴 수 없다. 33% 로 줄이고 흐리게 해도 세 방향(가로 / 얇은 세로 /
두꺼운 세로)이 유지되는 것까지 확인했다. 시트의 콜라이더·에이전트 값은 이미
돌아가는 `Crawler.cs` 의 커밋값을 그대로 옮긴 것이라 코드와 어긋나지 않는다.

MeshyAI 생성부터는 아직 하지 않았다. 시트가 그 입력이다.

**UI 에셋 1차 R&D와 Unity 임포트**를 Codex로 진행했다. 확정 기획과 적 시트의
동결압 팔레트를 기준으로 패널·체력·배터리·상호작용·피격 PNG를 만들고,
크로마 제거와 런타임 축소본 생성 과정을 스크립트로 남겼다. Unity MCP로 13개를
Sprite로 임포트해 투명도·압축·9-slice 값을 적용하고 실제 로드와 콘솔 오류까지
검증했다.

**달리기 스태미너와 튜토리얼 UI 확장**을 Codex로 진행했다. 스태미너는 정상·회복
대기 상태를 분리하고 구현 규칙과 이정범 담당 범위를 기획에 함께 기록했다. 실제
Input System 바인딩을 읽어 WASD·마우스·E/F/Shift/C/Space/R/1/2 안내 에셋과
조작법 목업을 만들었으며, 문구는 이미지에 굽지 않아 TextMeshPro로 교체 가능하게 했다.

**기획 기반 파티클 VFX 공용 키트**를 Codex로 만들었다. 눈보라·서리 먼지·총구
섬광·연료 화염·전기 스파크·폭발을 3·4·5·6장의 장면에 대응시키고, 이미지 생성
원본과 재현 가능한 마스크 제작 스크립트를 함께 남겼다. 데스크톱 WebGL 기준으로
ParticleSystem 최대 수와 금지 모듈을 정해 팀원이 프리팹을 바로 배치할 수 있게 했다.

**환경음 32종을 ElevenLabs API 로 만들어 Unity 에 넣었다.** 쓰던 Deevid 에 API 가
없어 자동화가 막히는 것을 먼저 확인하고 옮겼다. 웹 UI 에서 클릭한 작업은 흔적이
남지 않지만, 프롬프트를 스크립트에 박아두면 재생성이 명령 한 줄이고 그 파일 자체가
활용 근거가 된다. 무료 티어로 7 개를 뽑아 떼깔을 본 뒤 Starter 를 결제했다.

**결과를 귀로만 믿지 않고 파형으로 검증한 것이 두 번 결정적이었다.** 시험 생성한
루프 4 개 중 3 개에 페이드가 걸려 있었고, 프롬프트에 "constant level, no fade" 를
넣으니 8 개 중 8 개가 양호해졌다. 단발성은 더 심했다 — 생성기가 요청한 길이를
무음으로 채워 돌려주는 탓에 `light-switch-click` 은 1.48 초 중 앞 884ms 가 무음이라
스위치를 누르고 1 초 뒤에 소리가 났다. 잘라낼 지점은 귀로 정할 수 없어 진폭 포락선
으로 찾았고, 앞을 0 으로 붙이면 클릭 노이즈가 생겨 10ms 를 남겼다.

**막힌 곳은 Unity 임포트 설정이었다.** 기본 설정에 AAC 를 넣으면 Unity 가 조용히
PCM 으로 되돌린다. AAC 가 WebGL 전용 포맷이라 기본 플랫폼에서는 유효하지 않기
때문인데 경고가 없다. 그래서 WebGL 플랫폼 오버라이드로 넘겼더니 이번엔 32 개 전부
거부당했고, 필드를 하나씩 바꿔가며 `sampleRateSetting` 이 범인인 것을 찾았다.
설정한 뒤 되읽어 확인하지 않았으면 빌드 용량이 몇 배로 불어난 채 넘어갔을 것이다.

**장면별 배경음악 10 곡**을 같은 방식으로 뽑았다. 기획서의 「여섯 장소」를 프롬프트
근거로 삼아 장마다 성격을 갈랐고, 4 장에서 조명이 켜지는 순간과 발각되는 순간은
장 전체에 깔리는 트랙으로는 안 나오므로 큐로 따로 뺐다. 음악은 분당 900 크레딧으로
효과음보다 훨씬 비싸서, 짧은 것 하나로 엔드포인트를 검증한 뒤 나머지를 돌렸다.

**정작 오래 걸린 것은 음량 맞추기였다.** 크기가 제각각이라는 지적을 받고 재보니
앰비언스가 42.6 dB, 발소리가 56.7 dB 벌어져 있었다. 그런데 측정을 시작하자 그보다
큰 문제가 드러났다 — 일부는 볼륨이 낮은 게 아니라 **거의 무음으로 생성돼 있었다.**
`footstep-concrete-03` 은 피크가 -46.8 dBFS 였다. 공통점은 프롬프트에 `quiet` ·
`soft` · `almost silent` 가 들어간 것이었다. 조용한 소리를 요청했더니 정말 안 들리는
것을 준 것이고, 이건 증폭으로 못 고친다. 9 개를 다시 뽑았고 `close microphone` 처럼
**크기가 아니라 마이크 거리로 지시**하니 해결됐다. `footstep-concrete-01` 만 세 번
걸렸는데, 두 번은 같은 방향으로 고쳐 실패했고 「boot」 를 빼고 「Foley recording」 으로
틀 자체를 바꾸니 나왔다.

**정규화는 길이에 따라 방식을 갈라야 했다.** 처음에 전부 LUFS 로 맞추려 했더니 비슷하게
들리는 콘크리트 발소리 3 종이 -66 · -54 · -43 LUFS 로 나왔다. R128 이 3 초 이상을
전제로 게이트를 걸어서 1 초짜리는 신호 대부분이 버려진다. 긴 것은 LUFS, 짧은 것은
RMS 로 나누고, 피크 천장에 막혀 목표까지 못 올라가는 순간음에는 리미터를 걸었다.
편차가 앰비언스 0.0 dB · 구조물 0.9 dB · 발소리 4.3 dB 로 좁혀졌다.

세 번 다 같은 교훈이었다 — **생성 결과를 들어보기 전에 숫자로 먼저 확인해야 한다.**
루프의 페이드, 앞 무음, 무음 생성 셋 다 귀로는 원인을 짚을 수 없었고 파형을 재고 나서야
무엇을 고쳐야 하는지 알 수 있었다.

**상호작용 · 장치음 21 종**을 더하고 사운드 전체를 문서로 넘겼다. 소리를 기획서만
보고 짜지 않고 `Lever` · `Pickup` · `Carriable` 과 장치 세 패턴의 실제 API 를 읽어
파일 이름을 컴포넌트에 맞췄다. `TimedDevice` 에 `Started` 와 `Progress` 가 이미
있어서 시작 · 완료 두 지점이 코드에 존재했고, 소리도 그 둘로 갈랐다. 앞선 세 번과
달리 재생성이 0 회였는데, 「크기를 요청하지 말고 마이크 거리로 지시한다」 를 처음부터
적용했기 때문이다.

**문서는 `architecture.md` 가 스스로 정한 규칙에 따라 떼어냈다.** 오디오 절이 123 줄로
불어 「전체 지도가 안 보이면 개별 문서로 옮긴다」 는 조건에 걸렸다.
`docs/tech-design/audio.md` 로 옮기고 원문에는 링크와 요약만 남겼으며, 시스템 목록에
Audio 행과 「새 컨텐츠를 추가하려면」 에 사운드 절차를 넣어 다른 사람이 도달할 수 있게
했다. `plan.md` 의 32 종 기준 서술도 63 종으로 갱신했다. 문서에 적은 파일명 63 개가
실재하는지와 문서 간 링크가 살아 있는지는 스크립트로 대조해 확인했다 — 사람이 읽고
따라 하는 문서라 이름 하나가 틀리면 그 자리에서 막힌다.

**적 3종 소리 28 종**을 만들었다. 처음에는 `Crawler` 만 애니메이션 클립에 맞춰 9 개를
뽑았는데, 사용자가 「스펙 적어놓지 않았나」 고 물어 `docs/enemy-sheets/` 를 다시 보니
세 종 모두 클립 목록과 **프레임 단위 이벤트**까지 이미 확정되어 있었다. 내가 그것을
안 읽고 만든 것이라 다시 했다.

**스펙이 소리를 두 군데서 바꿨다.** 첫째는 재질이다. 명세가 표면을 「검은 회청색 균열
피부 + 흰 서리 흉터」로 고정하고 **「젖은 값은 아래쪽 입과 관절 최심부에만 3% 미만」**
이라고 못박았는데, 나는 몸 전체를 젖은 소리로 만들어 두었다. 몸통은 마른 서릿결이
갈라지는 쪽으로 바꾸고 젖은 소리는 입에서만 나게 했다. `Colossus` 는 「실제 석재·금속
재질 금지」 라 골렘이 아니라 같은 종의 확대이므로 돌 소리를 쓰지 않았다. 둘째는 공격
이벤트다. 명세가 **8f 예고 · 13f 히트**로 나눠 놓았는데 하나로 합쳐 두었던 것을 둘로
쪼갰다. 기획의 「예고가 있으면 억울하지 않다」가 이 0.17 초에 걸려 있다.

**생성기가 「끊기지 않는 소리」를 잘 못 만든다는 것도 알았다.** `clinger-scuttle-loop`
은 걷는 루프인데 **신호가 있는 구간이 1%** 였다. 「never silent」 를 넣어 32%, 동작이
아니라 **질감으로 묘사**하니 51% 가 되었다. 파형에서 「신호 구간 비율」을 재지 않았으면
루프가 거의 무음인 것을 모르고 넘겼을 것이다.

**문서가 코드를 깨뜨린 사고도 있었다.** `audio.md` 에 적어둔 발소리 예제가
`Random.Range` 를 그대로 써서, 그것을 가져다 쓴 `PlayerMotor.cs` 가 `System.Random` 과
충돌해 `CS0104` 로 컴파일이 깨졌다. 문서에 넣는 코드는 붙여넣는 순간 남의 파일에서
도는 코드라는 것을 잊었다. `UnityEngine.Random` 으로 고치고 이유를 함께 적었다.

**발각 큐를 버리고 추격 루프로 바꿨다.** 처음 만든 것이 오케스트라 현악 트레몰로라
나머지 아홉 곡의 드론·질감 결과 어울리지 않았고, 「공포는 앰비언스에서 나온다」는
방향과도 반대로 음악이 앞에 나섰다. 사용자가 「음산하고 ㅈ됐다가 느껴지게」 라고 한
것이 열쇠였다 — 그건 놀람이 아니라 **가라앉는 느낌**이고, 터지는 소리로는 안 만들어진다.
아래로 내려갈 것 · 끝에서 안 빠져나갈 것 · 화음을 어긋나게 할 것 셋으로 다시 잡았다.

**말로 안 되는 것을 파형에서 해결한 라운드였다.** 「no fade out」 을 넣어도 생성기는
끝에 decay 를 붙였고, 「금속을 얹어라」 와 「저역을 두껍게」 를 동시에 요구하면 한쪽만
줬다(저역 강조 → 고역 0.0%, 금속 강조 → 저역 4.8%). 그래서 프롬프트를 더 밀지 않고
**잦아들기 전에 끊고, EQ 로 대역비를 맞췄다.** 12 가지 EQ 를 자동으로 돌려 목표
무게중심 248 Hz 에 정확히 맞춘 것이 그것이다. 음악 API 에는 loop 파라미터가 없어
꼬리를 머리에 등파워 크로스페이드로 얹는 도구(`make_loop.py`)도 만들었다.

**루프의 어색함은 이음매가 아니라 음량 기울기였다.** 클릭이 없어도 트랙 안에서 음량이
오르내리면 한 바퀴마다 부풀었다 꺼지는 주기가 생긴다. 원형 이동 RMS 의 역수를 걸어
9.5 dB 를 2.5 dB 까지 폈다. 이득 곡선 자체가 순환해야 해서 신호를 원형으로 이어 붙인
상태에서 계산했다 — 안 그러면 애써 만든 이음매가 다시 깨진다.

**두 번 잃어버렸다.** 후보를 같은 이름으로 덮어써서 하나, 「정리해 달라」 를 넓게 읽어
비교본 두 개를 지워서 하나. 사용자가 그중 하나를 원했는데 복구가 안 됐다.
`AssetDatabase.DeleteAsset` 은 휴지통을 안 거치고 커밋 전이면 되돌릴 데가 없다.
다행히 지우기 전에 재둔 대역 수치가 남아 있어 그 값을 목표로 다시 만들어 무게중심
1393 Hz 를 1395 Hz 로 복원했다. **측정해서 적어 두는 습관이 파일을 대신했다.**
이후로는 후보를 스크래치패드에 백업하고 지우지 않는다.

**그리고 반복 실행이 파일을 갉는 것을 발견했다.** `trim_silence.py` 가 매번 전체를
훑어서, 이미 잘린 음악이 프레임 경계 때문에 수십 ms 씩 더 깎였다. 세 개가 실제로
짧아진 것을 커밋 직전에 잡아 되돌렸다. **잘라낼 양**을 기준으로 건너뛰게 고쳐 멱등하게
만들었다. 무음 길이로 판단하면 경계값에서 새어 나간다.

## 2026-08-09 · 2장 복도를 레퍼런스 분위기로 다시 세움 — Blender 모델링과 소품

회색 박스로 세운 2장 복도를 레퍼런스 컨셉아트(`docs/level-sheets/mockups/codex/
ch02-dormitory/v2-eerie/01-entry-wide.png`)에 맞춰 Blender 로 다시 만들었다. 지시는
「이 이미지 분위기대로, blender 로, 머터리얼도 사진 느낌으로, 단 이미 만든 경로는
크게 벗어나지 않게」 였다. 첫 결과를 보고 사용자가 **「너무 기본 도형으로만
만들어졌네」** 라고 했고, 그 한 줄이 이 라운드의 전부였다.

**「기본 도형처럼 보인다」 는 형태가 단순하다는 뜻이 아니었다.** 각이 살아 있고
그림자 선이 없다는 뜻이었다. 그래서 모든 파트에 Bevel(0.004~0.012, 2세그먼트)을
걸고, 배관을 박스에서 실제 원통으로 바꾸고, 벽을 판 하나가 아니라 「기본판 + 튀어나온
상하 레일 + 세로 배튼 6개」로 쪼개 칸이 **음푹 들어간 패널**로 읽히게 했다. 바닥은
널 16장을 폭 0.15~0.22 로 무작위, z 를 ±0.006, 기울기를 ±0.9° 흔들었다. 한 칸이
8,046 폴리곤이 됐다.

**Bevel 은 join 전에 적용해야 한다.** `join()` 은 활성 오브젝트의 모디파이어 스택만
남기므로, 160개를 합치기 전에 전부 `convert(target='MESH')` 로 굳혔다. 이걸 모르고
합치면 베벨이 하나만 남는다 — 정확히 「기본 도형」 으로 돌아간다.

**진짜 문제는 형태가 아니라 밀도였다.** 칸을 새 모듈로 통일하면서 사물함·침상
변형이 사라져 복도가 텅 비었다. 레퍼런스의 밀도는 벽에 붙은 물건에서 나온다.
사물함 3연(통풍 슬릿·세로 손잡이·걸쇠판·명찰 꽂이·경첩)과 이층침대(강관 프레임·
나무 발판·매트리스·구겨진 담요·베개·안전바·사다리)를 별도 FBX 로 뽑아 11개 배치했다.

**고쳐도 화면이 안 바뀌는 데 오래 걸렸다.** 소품이 회색 플라스틱처럼 밝아서 팔레트를
두 번 낮췄는데 둘 다 반영되지 않았다. Unity 가 프로젝트의 `.mat` 이 아니라 **FBX 내장
머터리얼**을 쓰고 있었고, 이름이 양쪽 다 `M_Ch2_Trim` 이라 인스펙터로는 구분이 안
됐다. `AssetDatabase.GetAssetPath` 가 `.fbx` 를 가리키는 것을 보고 알았다.
값을 의심하지 말고 **어느 에셋이 쓰이는지를 먼저 찍어보는 것**이 빨랐다.

**렌더로 판단하려면 렌더가 게임과 같아야 한다.** 내 촬영 리그의 손전등이 intensity 19
였는데 `Player.prefab` 은 6 이었다. 3배 밝은 화면을 보고 「창백하다」 고 판단해 팔레트를
필요 이상으로 어둡게 깎았다. 리그를 프리팹 값과 맞춘 뒤 다시 잡았다.

**소품은 NavMesh 를 끊는다.** 복도 안폭 2.8 m, Agent 반지름 0.5 라 마주 보는 소품
깊이 합이 1.8 m 를 넘으면 통로가 사라진다. 출입구는 더 좁아서 사물함이 방문을
0.22 m 물었을 때 `Room_Store` 경로가 `PathPartial` 로 떨어졌다. 배치를 바꿀 때마다
복도·문 앞·방 세 곳을 다시 재는 것으로 처리했다.

**「소 울음 같다」 는 지적을 파형에서 확인하고 고쳤다.** `crawler-vocal` 둘이 짐승
울음처럼 들린다는 말을 듣고 스펙트럴 플랫니스를 재보니 **0.0001** 이었다. 0 에
가깝다는 것은 음정이 완벽하게 또렷하다는 뜻이고, 그게 곧 포유류 발성의 특징이다.
귀로 느낀 것이 숫자에 그대로 있었다.

원인은 내 프롬프트의 단어였다. `moan` · `call` 이 생성기에게는 포유류 발성 신호다.
빼고 다시 뽑아 0.34 까지 올렸는데, `-02` 만 0.046 에 머물렀다. **`snarl` 하나를
남겨 뒀기 때문이다.** 목으로 내는 소리를 아예 지우고 턱과 뼈판이 부딪히는 물리적인
소리로만 지시하니 0.157 이 됐다. 지금 둘은 0.34(찢어지는 비명)와 0.16(뼈판
부딪힘)으로 결이 갈린다.

**고르는 기준을 한 번 잘못 세웠다.** 처음엔 「잡음일수록 좋다」 로 점수를 매겼는데,
그러면 그냥 쉭쉭거리는 소리가 이긴다. 실제로 7112 Hz 짜리를 골랐다가 형제들의
범위(플랫니스 0.03~0.39 · 무게중심 39~5800 Hz)와 대보고 범위 안쪽으로 바꿨다.
**최대화가 아니라 범위 안에 드는 것**이 기준이어야 했다.

**시작 화면 BGM 후보 셋을 뽑았다.** 기존 `title-theme` 이 있었지만 그 뒤로 레벨 시안과
VFX 방향이 확정됐으므로 그 기준으로 다시 봤다.

레벨 시안 문서에서 원칙 하나를 그대로 가져왔다 — 「음산함은 전체 노출만 낮추는 방식으로
만들지 않았다. 진행 장치의 작은 광원은 남기고, 그 빛이 닿지 않는 공간을 크게 두었다.」
**소리로 옮기면 다 지워서 어둡게 만들지 않고 작고 연약한 것 하나를 남기고 둘레를
비우는 것**이다. 기존 곡은 정반대였다 — 저역 81% 에 소리가 84% 구간을 채운 드론이라
빈 공간이 없었다. 미술 방향의 「미래 SF · 사이버펑크 아님」 제약도 프롬프트에 넣었다.
안 막으면 신스웨이브로 샌다.

셋의 차이를 「남기는 작은 것」으로 잡았다 — 중계소의 신호음(A) · 두고 간 피아노(B) ·
고도 그 자체(C). **A 는 실패했다.** 아무도 안 듣는 신호가 계속 나간다는 발상이 무대와
가장 잘 맞았는데, 생성기가 「thin repeating signal tone」 을 무시하고 드론만 줘서
기존 곡과 거의 같아졌다(고역 0.0%). C 가 소리 구간 64% 로 가장 비어 있어 원칙에 가깝다.

**「비어 있음」 을 수치로 잡을 수 있다는 것을 이번에 알았다.** 소리가 존재하는 구간의
비율을 재면 된다. 84% · 83% · 77% · 64% 로 네 곡이 줄을 서고, 그게 곧 「공간을 얼마나
비웠나」다. 밝기나 음량과 달리 이건 편곡의 성격을 직접 가리킨다.

## 2026-08-09 · 타이틀 설원 씬과 해상도 대응

「스타트 버튼 씬을 설원에 눈 내리는 걸로 만들어 줘」 로 시작했는데, **쓰던
파일이 도중에 다른 버전으로 바뀌었다.** UI 담당 세션이 같은 타이틀 화면을 코드로
짓고 있었던 것이다. 내 `TitleScreen` 은 덮였고 `OptionsPanel` 은 그쪽
「사운드 설정」과 같은 것을 두 벌 만드는 셈이 됐다.

**갈래를 다시 잡았다.** 그쪽 코드 주석에 「설원 렌더 위에 표시되는 타이틀 메뉴」
라고 적혀 있어서, 설원은 애초에 내 몫으로 기대되고 있었다. 내 옵션 패널은 지우고
3D 배경만 맡았다. 그리고 `TitleScreen.Awake` 가 **Canvas 자식을 전부 `Destroy`
한 뒤 UI 를 다시 짓는다**는 것을 발견해 `team-setup.md` 에 적었다 — 모르고 씬에
UI 를 배치하면 플레이할 때만 사라지고 씬에는 남아 있어 원인을 못 찾는다.

**해상도 문제는 짐작하지 않고 숫자로 잡았다.** 씬은 `MatchWidthOrHeight=0`(폭
기준)인데 코드가 Awake 에서 `0.5` 로 덮고 있어 **에디터와 플레이가 서로 달랐다.**
그리고 폭 기준 자체가 650×880 고정 패널에 안 맞았다.

```
2560x1080  폭기준 1173  넘침!   절반 1016   Expand 880
3440x1440  폭기준 1577  넘침!   절반 1360   Expand 1173
1920x800   폭기준  880  넘침!   절반  757   Expand 652
```

`Expand = min(w/1920, h/1080)` 는 어떤 비율에서도 기준 화면이 통째로 들어간다.
씬과 코드 양쪽을 그걸로 맞췄다. **한쪽만 고치면 다른 쪽이 되돌린다.**

**배경에서 배운 것 셋.**
- 평평한 판은 지평선이 자로 그은 선이 되어 눈밭으로 안 읽힌다. 격자를 접었다.
- 안개색을 카메라 배경색과 **같은 값**으로 둬야 지평선에 경계선이 안 생긴다.
- 눈은 「작고 많고 짧아야」 눈이다. 처음에 크게 만들었더니 파편처럼 보였고,
  꼬리(`velocityScale`)를 안 줄이면 빗금이 된다. 그리고 방출 상자가 카메라를
  감싸고 있으면 렌즈 앞에서 태어난 입자가 화면을 가로지르는 큰 줄로 찍힌다 —
  상자를 카메라 앞으로 밀어내 해결했다.

초광폭(21:9)에서 세상 끝이 보이지 않도록 먼 줄을 156m 까지 넓혔다. 수평 시야가
100° 를 넘으므로 화면 비율만 보고 폭을 잡으면 모자란다.

## 2026-08-09 · 타이틀에 그것의 실루엣을 세움

「대왕 몬스터 안 보이고 실루엣만 살짝 보이는 연출, 괴음도 있으면 좋겠다.
있는 리소스에서 찾아봐」

**찾을 게 없었다. 이미 그 용도로 만들어져 있었다.** `audio.md` 에
`colossus-distant-loop` 이 「1 장 창밖 — 루프. **실물 없이 실루엣만**」 이라고
적혀 있다. 요청한 연출을 위해 준비된 클립이나 마찬가지였고, `colossus-roar` 는
A 가 「아직 아무 데도 안 걸려 있다」 고 남긴 것이었다. 둘 다 여기서 처음 쓰였다.

**사라지는 방법을 반투명이 아니라 색으로 했다.** 반투명이면 뒤의 나무가 몸을
통과해 비쳐 유령이 되고 정렬 문제도 생긴다. `_BaseColor` 를 씬 안개색으로 밀면
**거리에 묻힌 것**으로 읽힌다 — 이 장면에서 원하는 쪽이 그거다. `MaterialPropertyBlock`
으로 넣어 공유 머터리얼은 안 건드린다.

**「살짝 보이는」 것과 「못 알아보는」 것은 다르다.** 처음에 46m 뒤에 8m 로
놓았더니 나무 사이 얼룩이 되어 무엇인지 안 읽혔다. 37m 로 당기고 11m 로 키워
머리가 수목한계선 위로 올라오게 하고, 앞을 가리던 나무 9그루를 치우고 나서야
네 다리로 버틴 덩치로 보였다. **형체는 알아보되 흐려야 한다.**

소리는 3D 로 뒀다. 실루엣이 오른쪽에 있으니 소리도 오른쪽에서 와야 한다 —
어디서 나는지가 이 연출의 절반이다.

**검증에서 시계를 쫓다가 두 번 놓쳤다.** 주기가 30 초인데 `execute_code` 호출
간격이 10~20 초라 매번 다른 구간을 잡았다. 시계를 맞추려 하지 말고 `Apply(0/0.5/1)`
과 `Roar()` 를 리플렉션으로 직접 불러 양 끝만 봤다 — visibility 0 이 안개색과
정확히 일치하고 1 이 실루엣색, `Roar()` 에 소리와 애니메이터 트리거가 함께
걸리는 것을 숫자로 확인했다. **주기적인 것을 검증할 때는 기다리지 말고 상태를
직접 만든다.**

**Colossus 걷는 소리가 안 들린다는 지적을 재보니 무게중심이 29 Hz 였다.** 노트북
스피커가 재생하지 못하는 대역이다. 거대함을 저역으로만 표현한 결과인데, 서브는 몸으로
느끼는 몫이고 **귀에 남는 것은 충격체(200~500 Hz)와 부스러기 소리**다. WebGL 로
배포하니 더 그렇다.

프롬프트를 고치니 이번엔 4633 Hz 로 튀어 자잘해졌다. **생성기는 무게와 충격체를 동시에
못 준다** — 금속과 저역, 정적과 무게에서 이미 세 번 겪은 같은 벽이다. 그래서 옛것과
새것을 **타격 지점을 맞춰 겹쳤다.** 정렬이 없으면 한 발이 두 번 밟는 소리가 된다.

**걷기 루프는 아예 발소리를 배열해 만들었다.** 네 번 요청해도 그 사이가 안 나와서
방식을 바꿨고, 명세의 `Walk_Knuckle`(54f/1.8s · 접지 넷)에 맞춰 0.45 초 간격으로
20 개를 놓았다. 생성으로 못 얻는 것을 조립으로 얻은 셈인데, 얻은 것이 더 있다 —
루프의 발소리와 애니메이션 이벤트로 칠 발소리가 **같은 소리**가 되고, 주기의 정수배라
이음매가 **구조적으로** 맞는다. 처음부터 이렇게 했어야 했다.

**「먹는 씬」 은 기획서에 있었다** — 「붙잡히면 한 번에 죽는다. 양손으로 붙들려 목이
뜯긴다.」 Colossus 만 하는 즉사다. 붙잡는 순간과 끝나는 순간을 둘로 나눴다. 한
덩어리면 타이밍을 못 맞추고 갑작스러움도 안 산다.

**타이틀과 엔딩을 확정했다.** 둘 다 44 초 루프다. 엔딩은 **두 생성물을 겹친 것**인데,
「아래에 묻힌 무게 + 위로 멀어지는 기계 소리 + 빈 공간」 셋을 동시에 못 받아서
따로 뽑았더니 마침 서로 다른 대역에 있었다. 대역이 갈리면 겹쳐도 자리를 안 뺏는다는
것이 이번에 반복해서 쓴 방법이다.

파일명은 바꾸지 않고 **내용만 덮어썼다.** Title.unity 가 이미 title-theme 을 물고
있어서 이름을 바꾸면 GUID 가 달라져 참조가 끊긴다.

**「크기에 비해 가볍다」 는 지적을 대역을 잘게 나눠 풀었다.** 앞서 무게중심을 183 Hz
까지 올려 놓고도 가볍게 들린다기에 20~60 · 60~120 · 120~250 처럼 잘라 재보니,
**에너지의 74% 가 20Hz 아래**에 있었다. 사람이 못 듣고 스피커도 못 내는 대역인데
헤드룸을 다 먹어서, 정규화할 때 정작 들리는 부분이 눌렸다. 「저역 96%」 라는 숫자가
오히려 문제를 가리고 있었던 셈이다.

32Hz 아래를 자르니 들리는 무게 대역(60~250 Hz)이 **3.0% 에서 34.1%** 가 됐다.
감쇠하는 저음 몸통을 합성해 얹는 것도 만들어 봤지만, 크기를 탐색해 보니 **안 얹는
쪽이 기준에 가장 가까웠다.** 있는 것을 더하는 것보다 **없어야 할 것을 빼는 것**이
답인 경우였다.

기준을 「무겁게 들리는 우리 소리」에서 가져온 것도 이번에 처음 했다. `hydrogen-
explosion` 의 대역 프로파일을 목표로 두니 얼마나 모자란지가 한눈에 보였다. 절대적인
좋은 값이 없는 문제에서는 **이미 통과한 소리를 자로 쓰는 것**이 통한다.

## 2026-08-09 · 소지품이 장을 넘어가게 함

「1장에서 손전등을 얻어도 다음 장으로 가면 보장이 안 된다. 모든 장에서 소지품을
그대로 넘겨줄 수 있나」

**원인은 단순했다.** 장마다 `Player` 가 새로 생기고, 씬에 놓인 프리팹은 `Awake`
에서 인스펙터 기본값으로 자기를 초기화한다. 1장에서 주운 손전등은 2장이 열리는
순간 「안 주운 상태 + 배터리 가득」 으로 리셋된다.

**플레이어를 `DontDestroyOnLoad` 로 살리는 방법은 안 썼다.** 그러면 장마다 놓인
`Player` 를 지우거나 옮기는 처리가 필요하고, 레벨을 만드는 쪽이 **씬에서
플레이어를 보고 배치를 맞추는 방식**을 못 쓰게 된다. 데이터만 옮기면 씬 구성은
지금 그대로다. `GameFlow` 가 이미 씬을 넘어 살아남고 `EnterChapter` 훅도 있어서
붙일 자리가 이미 있었다.

**되돌리기를 기존 함수로 못 한 것이 설계 포인트였다.** `PickUp` · `AddBattery` ·
`AddAmmo` 는 전부 **더하는** 함수인데 필요한 것은 **맞추는** 것이다. 더하기만
쓰면 1장에서 다 쓴 배터리가 2장에서 가득 차고, 탄창은 넣을 방법이 아예 없다.
A 의 스크립트에 `RestoreState` 두 개만 최소로 냈다.

**죽었을 때를 어떻게 할지가 진짜 결정이었다.** 나가는 순간을 항상 베끼면 죽을
때마다 배터리와 탄약이 되살아나 「죽어서 보충하기」가 된다. **장 이름이 바뀔
때만 베끼도록** 해서, 같은 장 재시작이면 보관된 것이 장 시작 시점의 것으로
남는다. 세 경우를 플레이로 확인했다.

```
Ch1 → Ch2    손전등 O / 배터리 97s / 권총 5+13   그대로 넘어옴
Ch2 → Ch6    배터리 42s / 장착한 권총까지 유지
Ch6 재시작   배터리를 5s 로 쓰고 죽어도 42s (장 시작값) 로 복귀
```

무기는 **종류로 짝을 맞춘다.** 배열 순서로 맞추면 어느 장에서 무기 칸 순서를
바꾸는 순간 권총 탄약이 산탄총으로 들어간다 — 그런 종류의 버그는 한참 뒤에
드러난다.

## 2026-08-09 · 타이틀 배경에 설산 능선

「타이틀에 산 모델도 들어왔으면 좋겠다」

**세 번 다시 만들었고, 매번 이유가 달랐다.**

첫 번째는 **판**이 됐다. 격자를 접어 만들었는데 앞 가장자리가 이미 최고 높이라
카메라를 향해 수직 절벽이 서 있었다. 산은 앞에서 뒤로 솟아야 한다 — 높이를
앞자락 0 에서 시작해 뒤로 가며 올리는 것으로 고쳤다.

두 번째는 **깊이가 문제였다.** 능선을 200m 깊이로 만들었더니 원점이 가운데라
앞자락이 카메라 뒤까지 왔다. 깊이를 0.3 으로 눌러 60m 로 만들자 앞자락이 나무
뒤(65m)에서 시작하고 봉우리가 100m 쯤에 섰다.

세 번째는 **구름**이 됐다. 봉우리가 화면 위로 잘려 나가면 산으로 안 읽힌다.
카메라 FOV 와 피치로 「100m 지점의 프레임 상단이 몇 m 인가」를 계산해 그 아래로
높이를 맞췄다. 눈으로 맞추지 않고 잰 것이 이번엔 빨랐다.

**진짜 배운 것은 안개와 거리의 관계다.** 밀도 0.021 의 ExponentialSquared 는
100m 를 완전히 지운다 — 멀리 두면 안 보이고, 보이게 하려고 당기면 화면을 채운다.
「멀리 두기」로는 원근을 못 만든다. 대신 **하늘보다 밝게** 뒀다. 눈 덮인 봉우리가
실제로 그렇고, 안개에 남는 얇은 몫으로 형태가 뜬다. 어두운 산이었으면 안개색에
그냥 묻혔을 것이다.

밀도를 0.014 로 조금 낮추면서 뒷줄 나무가 18% → 47% 로 또렷해졌길래, 나무 색을
어둡게 내려 깊이를 보전했다. **한 값을 건드리면 그 값이 지탱하던 것을 같이 본다.**

여기서 멈추지 않고 **키 없이 되는 폴리싱을 전부 했다.**

- **원고를 교신 기록 톤으로 다시 썼다.** 「여기는 트리라인 중계소. 사흘째 응답이
  없다.」 설명문에서 기록으로 바꾸니 같은 정보가 더 차갑게 읽힌다
- **목소리를 무전 교신음으로 가공했다.** 피치를 한 반음 내려 합성음 특유의 밝기를
  깎고, 무전 대역(320–3200 Hz) 필터를 **드라이와 섞었다.** 완전히 갈아치우면
  헤드폰에서는 그럴듯한데 노트북 스피커에서 뭉개진다 — 심사자가 듣는 환경이
  그쪽일 가능성이 높다. 전체에 캐리어 잡음을 아주 얕게 깔아 내레이션이 「얹은
  목소리」가 아니라 「들어온 신호」로 읽히게 했다. 무대가 신호 끊긴 중계소라
  임시방편이 아니라 설정과 맞는 선택이 됐다
- **타이밍을 코드에서 뺐다.** 자막 창과 믹스 위치가 4.61 같은 상수로 박혀 있었다.
  측정값을 `timing.json` 으로 내보내 자막과 믹스가 함께 읽게 바꿨다. 목소리를
  갈아 끼우면 **자막이 조용히 어긋나는 사고**가 구조적으로 안 난다

들어서 확인할 수 없으니 **측정으로 확인했다.** 말하는 구간이 빈 구간보다
8~12 dB 위에 있고, 전체 −16.9 LUFS · 트루피크 −1.3 dBFS 다.

IMPORTANT: Typecast 든 ElevenLabs 든 유효한 음성이 생기면 `vo01`~`vo07` 을 넣고
다시 돌리기만 하면 된다. 자막 · 믹스 · 음량이 알아서 따라온다.

## 2026-08-09 · 3장 연료 갱도 씬을 기획서와 시안대로 세웠다

레벨은 원래 C 담당인데 제출 영상에 공간이 없어 이번만 내가 만들었다. 팀에서
구두 합의했고, **작업 전에 경계를 표로 적어 커밋부터 했다** — 겹쳐 만드는 것이
가장 비싼 낭비다.

**미술을 지어내지 않았다.** `docs/level-sheets/mockups/codex/ch03-fuel-mine/` 의
네 시안을 먼저 읽고, 거기 있는 것만 만들었다 — 아치형 암반 통로, 철제 그레이팅
캣워크, 그 아래 수로, 붉은 안전등, 드럼통, 연료 펌프. 분위기 값도 지어내지 않고
**2장 씬에서 코드로 읽어 왔다.** 그런데 읽어 온 값이 오히려 문제가 됐다 — 2장의
주변광이 0.004 로 예외적으로 어두웠고(1장 0.300, 6장 0.115) 폭 7m 갱도에서는
공백이 됐다. **같게 맞추는 것과 맞는 값을 쓰는 것이 다르다는 걸 재보고 알았다.**

껍데기만 새로 만들고 소품 39개는 전부 기존 프리팹이다. 시안에 나오는 것이 이미
다 있었다.

**오래 걸린 곳은 NavMesh 였고, 원인이 네 개였다.** 굽고 나서 스폰→출구 경로를
계산했더니 `PathPartial` 이었다. 「구웠다」와 「이어졌다」는 다르다.

짐작을 네 번 했고 네 번 다 틀렸다. 그래서 **이등분으로 끊기는 z 좌표를 특정하고,
그 자리에서 x 를 훑어 무엇이 막는지 문자 그림으로 찍었다.** 그때부터는 한 번에
하나씩 잡혔다 — 수로 바닥이 두 번째 층이 되어 갈라졌고, 계단 발판이 에이전트
반경에 침식돼 사라졌고, **경사면의 렌더러를 지웠더니 콜라이더가 멀쩡한데도
굽기에서 빠졌고**(NavMesh 는 렌더러를 본다), 마지막은 **천장에 매단 작업등이
통로를 막고 있었다.** 갑판 위 여유가 1.88m 로 에이전트 높이 2.0m 에 모자랐다.

바닥 소품도 통로를 가로막고 있었는데, 이건 NavMesh 만의 문제가 아니라 사람도
못 지나가는 배치였다. **경로 검증이 레벨 버그를 잡아 준 셈이다.**

않았고 환경변수 하나로 다시 켜진다.
