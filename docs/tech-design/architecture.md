# 게임 시스템 구조

대부분은 아직 **세 사람이 동시에 붙기 위해 먼저 합의한 것**이다. 시스템 내부는
구현이 들어올 때부터 채우며, 2026-08-08 에 Player 가 첫 번째로 들어왔다.

무엇을 만드는지는 [`docs/game-design/treeline.md`](../game-design/treeline.md),
왜 이 순서인지는 [`decisions.md`](decisions.md), 누가 무엇을 맡는지는
[`docs/roles.md`](../roles.md) 에 있다.

## 여기에 담는 것 / 담지 않는 것

시스템 문서가 늘어나면 같은 시스템을 두 곳에서 설명하게 되고, 코드를 고칠 때
한쪽만 갱신되어 어긋난다. 경계를 이렇게 둔다.

| | 담는 것 |
| --- | --- |
| 이 문서 | 시스템 **목록과 책임**, 시스템 **간** 관계와 데이터 흐름, 새 컨텐츠 추가 절차 |
| `<시스템>.md` | 그 시스템 **내부** 동작과 확장 방법 |

**관계는 이 문서, 내부는 개별 문서.**

개별 문서는 미리 만들지 않는다. 이 문서를 훑을 때 특정 시스템 설명이 길어서
전체 지도가 안 보이면, 그때 `docs/tech-design/<시스템>.md` 로 떼어내고 여기에는
링크와 한 줄 요약만 남긴다.

IMPORTANT: 구조를 바꾸는 변경은 이 문서 갱신을 **같은 커밋**에 담는다.

## 씬은 한 사람만 만진다

IMPORTANT: 이 프로젝트에서 병렬 작업을 막는 유일한 구조적 장애물이다.

`.unity` 와 `.prefab` 은 두 사람이 동시에 고치면 병합할 수 없다. GUID 와 fileID 가
얽혀 있어 겉보기에 맞춰놔도 씬이 조용히 깨진다. 그래서 규칙은 하나다.

**한 씬에는 한 사람.** 남에게 줄 것은 씬이 아니라 **프리팹으로 준다.**

적을 배치해야 하면 적 담당이 프리팹을 만들어 넘기고, 레벨 담당이 자기 씬에
끌어다 놓는다. 이러면 두 사람이 같은 파일을 건드릴 일이 생기지 않는다.

각자 실험은 `Assets/Game/_Sandbox/<이름>.unity` 에서 한다. 남의 샌드박스를 열지
않는다.

## 씬 말고도 병합되지 않는 파일이 있다

`ProjectSettings/` 아래 몇 개는 **셋이 다 건드려야 하는데 병합이 안 된다.** 씬만
조심하면 된다고 생각하기 쉬운 자리다.

특히 레이어가 위험하다. 레이어는 씬과 프리팹에 이름이 아니라 **번호로** 저장된다
(`m_Layer: 8`). 각자 같은 번호에 다른 이름을 넣고 한쪽이 rebase 로 밀리면
오브젝트가 조용히 엉뚱한 레이어로 바뀌고, 레이캐스트가 어긋나기 시작한다.

그래서 2026-08-08 에 **쓸 레이어를 미리 다 잡고 담당별로 번호 구간을 나눴다.**

때문이다. 운반물은 들었을 때 플레이어와 안 부딪혀야 하고, 장치는 발동 대상이다.
마스크로 합칠 수는 있어도 나눈 것을 나중에 쪼갤 수는 없다.

코드에서 번호를 직접 쓰지 않는다. `Shared/GameLayers.cs` 를 쓴다. 그 파일과
`TagManager.asset` 은 **같은 커밋**에 담는다.

### 물리 충돌 매트릭스

레이어만 만들고 `DynamicsManager.asset` 을 안 만지면 전부 서로 부딪힌다.

| 끄는 조합 | 이유 |
| --- | --- |
| `Enemy` ↔ `Enemy` | 여럿 나올 때 서로 밀어내며 엉킨다 |
| `ViewModel` ↔ 전부 | 렌더 전용이라 물리가 없다 |
| `Trigger` ↔ `Player` 외 전부 | 트리거는 플레이어만 감지한다 |
| `Carriable` ↔ `Player` | 들고 걸을 때 자기 몸에 걸린다 |

### NavMesh 는 캐릭터를 빼고 굽는다

`NavMeshSurface` 의 `layerMask` 기본값은 **전부 포함**이다. 그대로 구우면 씬에 놓인
플레이어와 적 캡슐까지 걷는 면이 된다. 원점을 샘플하면 바닥(`y≈0`)이 아니라 캡슐
윗면(`y≈0.9`)이 잡히고, 경로 계산이 `PathInvalid` 로 조용히 실패한다. 에러도 경고도
안 뜬다.

굽기 전에 `Player` · `ViewModel` · `Enemy` · `Trigger` 를 뺀다.

```csharp
surface.layerMask = ~((1 << GameLayers.Player) | (1 << GameLayers.ViewModel)
                    | (1 << GameLayers.Enemy)  | (1 << GameLayers.Trigger));
```

IMPORTANT: **구운 데이터를 씬에 묻으면 씬 파일 전체가 바이너리가 된다.** Asset
Serialization 을 `Force Text` 로 두어도 그렇다. 커밋 기록이 제출물인데 씬 diff 가
통째로 사라지고, 그 씬은 병합도 불가능해진다. 실제로 2026-08-08 에 한 번 밟았고
씬을 이전 커밋에서 복원해야 했다.

`BuildNavMesh()` 뒤에 데이터를 별도 에셋으로 뗀다.

```csharp
if (surface.navMeshData != null && !AssetDatabase.Contains(surface.navMeshData))
    AssetDatabase.CreateAsset(surface.navMeshData, "<씬폴더>/NavMesh/<이름>.asset");
```

에디터 UI 에서 `Bake` 버튼으로 구우면 Unity 가 알아서 이렇게 한다. **스크립트로
구울 때만 직접 해야 한다.**

C 가 `Ch1` · `Ch2` · `Ch6` 을 구울 때도 같다.

IMPORTANT: **`BuildNavMesh()` 는 새 객체를 만든다. 기존 에셋에 복사해 넣어야 한다.**
`AssetDatabase.Contains` 가 거짓이면 아직 어느 파일에도 안 붙은 것이고, 그대로 두면
**메모리에만 남았다가 씬을 다시 열 때 사라진다.** 겉으로는 구운 것처럼 보이지만
디스크에는 옛 데이터가 그대로 있다. 2026-08-09 에 2장에서 이걸로 한 번 속았다 —
복도를 큐브로 바꿔놓고 다시 구웠는데, 저장된 NavMesh 는 옛 FBX 바닥 높이를 따르고
있었다.

```csharp
var saved = AssetDatabase.LoadAssetAtPath<NavMeshData>(path);
if (surface.navMeshData != null && !AssetDatabase.Contains(surface.navMeshData) && saved != null)
{
    EditorUtility.CopySerialized(surface.navMeshData, saved);   // 같은 GUID 를 지킨다
    surface.navMeshData = saved;
    EditorUtility.SetDirty(saved);
}
```

`CreateAsset` 이 아니라 `CopySerialized` 인 이유는 **GUID 를 지키기 위해서**다. 새로
만들면 씬의 참조가 바뀌어 diff 가 크게 나고, 남이 받을 때 충돌한다.

### 런타임에 막는 것은 굽기에서 뺀다

IMPORTANT: **`NavMeshObstacle` 로 막을 물건은 구울 때 꺼야 한다.** 굽기가 렌더 메시를
읽으므로(`useGeometry = RenderMeshes`) 그 물건의 **보이는 메시가 구멍을 파버린다.**
그러면 런타임에 그것을 치워도 **구멍이 그대로 남아 길이 안 열린다.** carving 은 이미
뚫린 구멍을 메우지 못한다.

2026-08-09 에 2장 얼어붙은 문이 정확히 그랬다. 히터로 얼음을 녹여도 경로가 안 열려서
**적이 따라 들어올 수 없었다** — 셔터로 도망칠 이유가 사라지는 자리다.

```csharp
door.SetActive(false);
surface.BuildNavMesh();      // 문이 없는 상태로 굽는다
door.SetActive(true);        // carving 이 런타임에 판다
```

`NavMeshModifier.ignoreFromBuild` 는 이 경우에 안 먹었다. **오브젝트를 끄는 편이
확실하다.** 캐릭터를 빼고 굽는 것과 같은 이야기다.

### 몸이 큰 적은 에이전트 타입을 따로 쓴다

NavMesh 는 **에이전트 타입 하나에 대해 하나씩 구워진다.** `NavMeshAgent.radius`
를 올려도 경로는 안 바뀐다 — 그 값은 회피와 조향에만 쓰이고, 경로는 구워둔 면을
그대로 읽기 때문이다. 몸이 큰 적을 제대로 걷게 하려면 **타입을 하나 더 만들고
그 타입으로 한 번 더 구워야** 한다.

| 타입 | ID | 반경 | 높이 | 쓰는 것 |
| --- | ---: | ---: | ---: | --- |
| `Humanoid` | 0 | 0.5 | 2.0 | `Crawler` · `Clinger` |
| `Colossus` | -1372625422 | 2.4 | 4.4 | `Colossus` |

IMPORTANT: **`Colossus` 가 등장하는 씬에는 `NavMeshSurface` 가 둘 있어야 한다.**
같은 GameObject 에 컴포넌트를 두 개 붙이고 `agentTypeID` 만 다르게 둔다. 데이터는
`<씬>.asset` 과 `<씬>_Colossus.asset` 으로 따로 뗀다. 하나만 있으면 그 적은
경로를 못 찾아 제자리에 선다. **에러도 경고도 안 뜬다.**

IMPORTANT: **반경 2.4 는 지름 4.8m 다.** 통로가 5.5m 면 가운데 0.7m 만 남아
NavMesh 가 조각조각 끊긴다. **통로는 7m 이상**으로 잡는다. 벽뿐 아니라 엄폐물
모서리끼리의 **대각선 간격**도 같이 봐야 한다 — 6장에서 히터와 엄폐물이 z 로
어긋나 있는데도 대각선이 0.9m 로 좁아 북서쪽이 통째로 섬이 되었다.

기하를 고쳤으면 **두 면을 다 다시 굽는다.** 하나만 구우면 플레이어와 적이 서로
다른 지형 위를 걷는다.

### 레이캐스트 마스크

레이어를 나눠도 각자 다른 마스크를 쓰면 의미가 없다. 세 개로 고정한다.

| 용도 | 마스크 | 쓰는 쪽 |
| --- | --- | --- |
| 상호작용 조준 | `GameLayers.Interaction` | A 가 쏘고 C 가 받는다 |
| 사격 | `GameLayers.Shot` | A |
| 적 시야 | `GameLayers.EnemySight` | B |

`Trigger` 와 `ViewModel` 은 **어느 마스크에도 들어가지 않는다.**

세 개는 **공용** 마스크다. 한 컴포넌트만 쓰는 마스크는 `GameLayers` 에 올리지
않고 그 자리에서 만든다. `Shared/` 변경은 셋의 합의가 필요한데, 쓰는 곳이 하나면
합의할 것이 없기 때문이다. 지금 그런 것이 하나 있다 — `PlayerMotor` 가 웅크린 뒤
일어설 수 있는지 볼 때 쓰는 천장 검사 마스크이며, `Player` · `ViewModel` ·
`Trigger` 를 뺀 나머지다. 두 번째 담당이 같은 것을 필요로 하면 그때 올린다.

URP 의 Rendering Layers 는 이것과 별개다. 손전등이 특정 물체만 비추게 하려면 그때
따로 잡는다. 지금은 쓰지 않는다.

### 태그는 늘리지 않는다

Unity 빌트인 `Player` 태그로 충분하다. 적은 `FindWithTag("Player")` 로 플레이어를
잡는다. 태그를 늘리면 문자열 오타가 컴파일을 통과해 런타임까지 간다.

### 씬 목록

`EditorBuildSettings.asset` 도 셋이 다 건드린다. 씬을 추가하면 여기 등록해야
한다. 샌드박스 씬은 빌드에 넣지 않는다.

2026-08-08 에 넷을 등록했고 2026-08-09 에 `Ch3`(B) · `Ch4`(A) 가 붙었다.

| # | 씬 | `Chapters.Order` |
| --- | --- | --- |
| 0 | `Game/Levels/Title.unity` | 아니다 |
| 1 | `Game/Levels/Ch1.unity` | 들어 있다 |
| 2 | `Game/Levels/Ch2.unity` | 들어 있다 |
| 3 | `Game/Levels/Ch3.unity` | **아직 아니다** |
| 4 | `Game/Levels/Ch4.unity` | **아직 아니다** |
| 5 | `Game/Levels/Ch6.unity` | 들어 있다 |
| 6 | `Game/Levels/Ending.unity` | 아니다 |

IMPORTANT: **빌드 목록에 있는 것과 `Chapters.Order` 에 있는 것은 다르다.** 짓는
중인 장은 빌드 목록에만 올린다 — 그래야 이름으로 열어 확인할 수 있으면서 관통은
안 건드린다. `Order` 에 먼저 끼우면 앞 장의 출구가 미완성 장으로 이어져 **지금
되는 관통이 끊긴다.** `Ch3` 와 `Ch4` 가 그 상태다. 이어지면 그때 `Order` 를 고친다.

IMPORTANT: **이 파일은 셋이 동시에 건드린다.** 3장과 4장이 같은 날 각자 등록하다
충돌이 났다. 붙일 때는 **빌드 목록만 상대 것을 통째로 받고 자기 씬을 에디터에서
다시 등록한다** — YAML 을 손으로 합치지 않는다.

`Title` 이 맨 앞이어야 게임이 거기서 시작한다. 순서가 바뀌면 빌드가 엉뚱한 씬으로
열린다. `Title` 과 `Ending` 은 `Chapters.Order` 에 넣지 않는다 — 장이 아니라서
`GameFlow` 가 플레이어를 찾거나 배치하려 들면 안 된다.

`Ending` 은 마지막 장을 빠져나온 뒤 가는 곳이다. 없으면 `Ch6` 의 출구가 갈 데가
없어 관통이 끝에서 끊긴다. 지금은 검은 화면뿐이고 UI 담당이 채운다.

IMPORTANT: 씬은 **인덱스가 아니라 이름으로** 로드한다 (`LoadScene("Ch1")`).
인덱스로 하면 목록 순서가 바뀔 때마다 엉뚱한 씬이 열린다. 위 번호는 등록 결과일
뿐이고 코드는 이 번호를 쓰지 않는다.

## 폴더 구조

```
Assets/Game/
├── _Sandbox/         각자 실험용 씬. 소유자 외 접근 금지
├── Levels/           장별 씬. Ch1 · Ch2 · Ch6 (그 뒤 Ch3 · Ch4 · Ch5)
│   └── Ch6/          그 장에서만 쓰는 스크립트. 씬 옆에 둔다
├── Player/           이동 · 카메라 · 손전등 · 체력 · 무기
├── Enemy/            적 · NavMesh · 상태 머신
├── Interaction/      문 · 레버 · 밸브 · 획득 · 운반
├── Devices/          장치. 즉시 발동 / 시간 발동 / 지속 상태 세 패턴
├── Progress/         씬 전환 · 체크포인트 · 사망 · 재시작
├── UI/               타이틀 · 설정 · 엔딩 · HUD · 로딩
├── Audio/            환경음. 어느 담당에도 속하지 않고 모든 장에서 쓴다
└── Shared/           인터페이스 3종과 `GameLayers`. 변경은 셋의 합의가 필요하다
```

`Assets/ThirdParty/` 는 제3자 에셋 원본 자리이고 저장소에서 제외된다.
정책은 `CLAUDE.md` 참고.

### 한 장에서만 쓰는 스크립트는 씬 옆에 둔다

`Levels/<장>/` 이 그 자리다. 처음 생긴 것은 `Levels/Ch6/CableCarDeparture.cs` 다.

시스템 폴더(`Player/` · `Devices/` · `Progress/`)는 **여러 장이 함께 쓰는 것**만 담는다.
장 하나의 마지막 연출을 거기에 넣으면 다음 사람이 「이건 어디서 쓰나」를 찾게 되고,
담당 폴더 규칙(한 폴더에 한 사람)도 장 담당과 어긋난다. 두 번째 장이 같은 것을
필요로 하면 그때 시스템 폴더로 올린다.

### 월드 배경은 아직 정하지 않았다

월드 배경(벽 · 바닥 · 구조물)을 어디서 조달하고 어떻게 통일할지는 아직 정하지
않았다. R&D 지시서가 [`world-assets.md`](world-assets.md) 에 있고, 결론이 나면
폴더 위치와 머티리얼 규약이 이 문서로 들어온다.

### AI 로 만든 에셋은 담당 폴더에 둔다

기획은 적 3종 · 소품 · 사운드를 AI 로 생성한다. **이것은 제3자 에셋이 아니라 우리
것이므로 `ThirdParty/` 가 아니라 담당 폴더에 넣고 커밋한다.** 커밋하지 않으면 셋이
각자 다른 모델을 갖게 되고, 같은 프리팹이 사람마다 다른 것을 가리킨다.

```
Assets/Game/Enemy/
├── Crawler.prefab
├── Crawler.cs
├── Models/           Crawler.fbx
└── Textures/         Crawler_BaseMap.png
```

- **만든 사람의 담당 폴더**에 둔다. 적 모델은 `Enemy/`, 무기 · 손전등은 `Player/`,
  레버 · 계기판은 `Interaction/` 또는 `Devices/` 다
- 파일 이름은 **쓰는 프리팹과 같게** 한다. `Crawler.prefab` ↔ `Crawler.fbx`
- 남이 쓰는 것은 자유다. 폴더 규칙은 **같은 파일을 둘이 고치는 것**을 막으려는
  것이지 참조를 막으려는 것이 아니다

**용량은 신경 쓰지 않고 원본 그대로 넣는다.** 저장소 용량과 빌드 용량은 별개다.
Unity 는 임포트 설정에 따라 텍스처를 압축하고 메시를 최적화해서 굽기 때문에, 4K
원본을 넣어도 빌드에는 설정한 크기로 들어간다. 원본을 미리 줄이면 나중에 더
키우고 싶을 때 되돌릴 수 없다.

빌드가 무거워지면 **원본이 아니라 임포트 설정을 만진다** — 텍스처의 `Max Size` 와
압축 포맷이다. WebGL 이라 빌드 용량이 곧 심사자의 첫 로딩 시간이므로, 배포 전에
한 번 보는 것으로 충분하다.

### 여러 장이 함께 쓰는 파티클은 `VFX/`에 둔다

눈보라 · 서리 먼지 · 총구 섬광 · 화염 · 스파크 · 폭발은 여러 담당자의 장에
재등장하므로 특정 장 폴더에 두지 않는다.

```text
Assets/Game/VFX/
├── Textures/    알파 PNG
├── Materials/   URP Particles/Unlit
└── Prefabs/     PS_<효과이름>.prefab
```

각 프리팹의 쓰임과 WebGL 예산은 [`../vfx-assets/README.md`](../vfx-assets/README.md)에
있다. 씬 소유자는 원본 프리팹을 복제하지 않고 인스턴스의 Shape 크기만 조절한다.

### 사운드는 `Audio/` 에 카테고리로 나눠 둔다 → [`audio.md`](audio.md)

사운드만 예외로 담당 폴더에 넣지 않는다. 눈보라 · 발소리 · 셔터 소리는 특정
담당의 것이 아니라 **여러 장에 재등장하며 함께 쓰는 것**이라, 담당 폴더에 넣으면
셋 다 남의 폴더를 참조하게 되어 규칙이 무의미해진다.

```
Assets/Game/Audio/
├── Ambience/     지속 배경음. 파일명이 -loop 로 끝나면 이음매 없이 반복된다
├── Footsteps/    표면별 발소리. 표면당 2종
├── Structure/    문 · 계단 · 창 · 배관
├── Electrical/   조명 · 차단기 · 정전과 복구
├── Interaction/  레버 · 밸브 · 획득 · 운반
├── Devices/      장치. 세 패턴에 맞춰 나뉜다
└── Music/        장면별 배경음악
```

63 개가 들어 있고 임포트 설정까지 끝났다. **무엇이 있고 어떻게 쓰는지, 새로
만들려면 무엇을 거치는지는 [`audio.md`](audio.md) 에 있다.** 붙이기 전에 그것을
본다 — 카테고리마다 `AudioSource` 설정이 다르고, 볼륨은 파일이 아니라 코드에서
정하게 되어 있다.

**적 · 무기 소리는 여기 두지 않는다.** 그것들은 담당 폴더로 간다.

## 서로 붙는 지점

**이 세 개만 고정하면 서로의 구현을 몰라도 각자 진행된다.** 최소한으로 잡았고,
바꾸려면 셋이 합의한다.

| 인터페이스 | 만드는 쪽 | 쓰는 쪽 |
| --- | --- | --- |
| `IInteractable` | 상호작용 담당 | 플레이어가 바라보는 대상에 호출 |
| `IDamageable` | 공용 | 플레이어와 적이 서로에게 호출 |
| `IDeviceTrigger` | 장치 담당 | 레버 · 스크립트 이벤트가 장치를 발동 |

`IDamageable` 을 양쪽이 함께 쓰는 이유는, 총이 적을 죽이는 것과 적이 플레이어를
때리는 것이 같은 모양이기 때문이다. 하나로 두면 A 와 B 가 서로를 기다리지 않는다.

## 남에게 넘기는 프리팹

씬 대신 프리팹으로 주고받으므로 **경로와 이름을 미리 박아둔다.** 나중에 이름을
바꾸면 이미 참조를 건 쪽이 전부 깨진다.

| 프리팹 | 만드는 쪽 | 쓰는 쪽 | 언제 |
| --- | --- | --- | --- |
| `Player/Player.prefab` | A | B 는 추격 대상으로, C 는 레벨에 배치 | 1단계 |
| `Enemy/Crawler.prefab` | B | C | 1단계 |
| `Enemy/Colossus.prefab` | B | 6장 담당 | 2단계 |
| `Enemy/Clinger.prefab` | B | 4 · 5장 담당 | 3단계 |

기획의 「기는 것 · 큰 것 · 매달린 것」이 각각 `Crawler` · `Colossus` · `Clinger`
다. 프리팹 이름은 영문 PascalCase 로 쓰고, 폴더는 만드는 쪽의 담당 폴더다.

IMPORTANT: **A 는 `Player.prefab` 을 완성 전에 먼저 올린다.** 캡슐에
`CharacterController` 와 `Player` 태그만 붙은 껍데기여도 된다. B 의 적은 추격할
대상이 있어야 하고 C 의 관통 확인에는 Player 와 Enemy 가 둘 다 필요하다. 완성을
기다리면 두 사람이 자기 샌드박스에서 아무것도 검증하지 못한다.

## 새 컨텐츠를 추가하려면

### 새 사운드

1. `docs/sound/gen_sfx.py` 의 `PROMPTS` 에 프롬프트를 적는다. **크기를 요청하지
   말고 마이크 거리로 지시한다** — 「quiet」 를 넣으면 안 들리는 것이 온다
2. 생성 → 무음 제거 → 음량 맞추기 → 임포트 설정 순으로 거친다. 중간을 건너뛰면
   트리거와 소리 사이에 지연이 남거나 크기가 어긋난다
3. `docs/assets.md` 에 그 자리에서 기록한다

명령과 함정은 [`audio.md`](audio.md) 에 있다.

### 새 장(레벨)

1. `Assets/Game/Levels/Ch<번호>.unity` 를 만든다. **그 씬의 소유자는 만든 사람**이다
2. 필요한 것은 다른 담당이 만든 **프리팹을 배치**한다. 로직을 씬에 직접 쓰지 않는다
3. 장 진입 · 이탈은 `Progress/` 의 씬 전환을 쓴다
4. `Chapters.Order` 에 넣고 빌드 씬 목록에도 등록한다. 둘 중 하나만 하면 조용히
   어긋난다

씬에 무엇을 두는지는 아래 「Progress」 절의 표를 따른다.

IMPORTANT: `ChapterExit` 의 `BoxCollider` 는 **`size` 를 직접 확인한다.** MCP 로
컴포넌트를 붙이면서 준 `size` 가 반영되지 않고 `(1,1,1)` 로 남는 일이 있었다.
1m 큐브라 통로를 못 막고, 플레이어가 옆으로 지나가면 장이 안 넘어간다. 겉으로는
멀쩡해 보여서 알아채기 어렵다.

### 새 적

1. `Assets/Game/Enemy/` 에 프리팹으로 만든다
2. `IDamageable` 을 구현한다. 그래야 총에 맞는다
3. 레벨에는 **프리팹만 넘긴다.** 남의 씬에 직접 배치하지 않는다

### 새 장치

1. 빈 오브젝트에 세 컴포넌트 중 하나를 붙인다 — `InstantDevice` · `TimedDevice` ·
   `SustainedDevice`. 레이어는 `Device`(18) 다
2. `enables` 에 발동하면 켜질 것을, `disables` 에 꺼질 것을 넣는다
3. 발동시킬 `Lever` 의 `devices` 에 그 장치를 넣는다
4. **새 스크립트를 만들지 않는다.** 셋으로 안 되는 것이 나오면 왜 안 되는지를 먼저
   확인한다. 장치마다 클래스를 만들면 아홉 개가 되고 그중 여덟은 서로 복사본이 된다

자세한 것은 [시스템 목록의 Devices](#devices).

### 새 획득물 · 운반물

새 스크립트를 만들지 않는다. 빈 오브젝트에 `Pickup` 이나 `Carriable` 을 붙이고 값만
채운다. 자세한 것은 [시스템 목록의 Interaction](#interaction).

### 새 상호작용 대상

위 셋으로 안 되는 것만 `IInteractable` 을 직접 구현한다. 구현하면 플레이어 쪽 수정
없이 붙는다.

### Player

`Assets/Game/Player/`. 컴포넌트를 하나씩 나눠 `Player.prefab` 루트에 모두 붙였다.
하나가 커지면 그때 쪼갠다.

| 컴포넌트 | 책임 |
| --- | --- |
| `PlayerInputReader` | 입력을 읽는 **유일한** 곳. 나머지는 여기만 참조한다 |
| `PlayerMotor` | 걷기 · 달리기 · 웅크리기 · 점프. 중력, 콜라이더 높이, 스태미너, 내는 소리 |
| `PlayerLook` | 좌우는 몸체, 상하는 카메라. 포인터 잠금 · 반동 · 흔들림 · 놀람 |
| `PlayerHealth` | 체력 3칸. `IDamageable` 구현 |
| `WeaponSwitcher` | 어느 총을 드는가. 양손 운반 중 총 잠금 |
| `PlayerWeapon` | 총 한 자루. `GameLayers.Shot` 레이캐스트, 탄창 · 재장전, 반동 |
| `PlayerInteractor` | `GameLayers.Interaction` 조준, `IInteractable` 호출 |
| `Flashlight` | 조명 토글과 배터리 소모 |
| `PlayerFootsteps` | 발소리 · 도약 · 착지. 이동 거리로 내고 표면은 장마다 정한다 |
| `PlayerHud` | 체력 · 탄약 · 배터리 · 스태미너 · 조준점 · 상호작용 문구 · 피격 오버레이 |

프리팹 구조는 이렇다.

```
Player                  태그 Player, 레이어 Player(8)
├── Body                회색 박스 캡슐
├── Camera              본 카메라. Player 와 ViewModel 을 그리지 않는다
│   ├── ViewModelCamera URP 오버레이. ViewModel(9) 만, 깊이를 지우고 겹쳐 그린다
│   ├── Flashlight      Spot Light. ViewModel 은 안 비춘다
│   ├── ViewModelLight  총만 비추는 약광. ViewModel(9) 전용
│   ├── Pistol          PlayerWeapon + Model
│   └── Shotgun         PlayerWeapon + Model
└── HUD                 Screen Space Overlay 캔버스 (1920×1080 기준, Match 0.5)
    ├── Health          체력 칸 3개. 좌하단
    ├── Stamina         Frame + Fill. 체력 위
    ├── Battery         Frame + Fill. 우하단
    ├── Ammo            눈금 8개 + 여분 문구. 배터리 위
    ├── Crosshair       조준점. 상호작용 대상이 있으면 스프라이트를 갈아끼운다
    ├── Interact        키캡 + 동사. 중앙 아래
    └── DamageOverlay   화면 전체. 평소 `enabled = false`
```

`PlayerWeapon` 만 루트가 아니라 `Camera` 밑에 **총마다 하나씩** 붙는다
(`Camera/Pistol` · `Camera/Shotgun`). 권총과 산탄총은 클래스가 아니라 **값만
다르다** — 산탄총은 탄자 수를 늘리고 퍼짐을 벌린 것이다. 장치를 세 패턴으로
수렴시킨 것과 같은 기준이고, 세 번째 총이 생겨도 값만 채우면 된다.

전환은 `WeaponSwitcher` 가 `PlayerWeapon` 컴포넌트를 켜고 끄는 것으로 한다. 꺼진
무기는 `Update` 가 돌지 않아 입력을 보지 않으므로, 총마다 "내가 장착됐나" 를
확인하는 분기가 없다. 사망 처리가 입력 컴포넌트 하나만 끄는 것과 같은 방식이다.

반동은 무기가 직접 카메라를 돌리지 않고 `PlayerLook.AddRecoil` 로 값만 넘긴다.
카메라 회전을 만지는 곳이 둘이 되면 매 프레임 서로 덮어쓴다.

`PlayerLook.Shake()` 도 같은 자리다. **인자가 없는 것은 인스펙터의 `UnityEvent` 에
그대로 걸기 위해서**이며, 세기와 길이는 `PlayerLook` 이 갖고 부르는 쪽은 「놀랐다」만
알린다. 6 장에서 `Colossus.noticed` 가 이것을 부른다.

**1인칭 총 모델은 별도 카메라로 그린다.** `ViewModelCamera` 는 URP 오버레이라
본 카메라 위에 깊이를 지우고 겹쳐 그린다. 총이 벽에 파고들지 않고, 시야각을 따로
줄 수 있어(본 카메라 70도 / 뷰모델 50도) 총이 덜 왜곡된다. 그래서 본 카메라의
컬링 마스크에서 `ViewModel`(9) 을 뺐다 — **둘 다 그리면 총이 두 번 그려진다.**

IMPORTANT: **손전등도 `ViewModel` 을 비추지 않는다.** 손전등과 총이 0.36m 밖에
안 떨어져 있어 역제곱 감쇠로 총이 하얗게 날아간다. 대신 `ViewModelLight` 라는
약한 점광을 `ViewModel` 전용으로 따로 둔다. 이것이 없으면 정전 상태에서 자기 총이
아예 안 보인다. 세기를 바꿀 때는 손전등이 아니라 이쪽을 만진다.

총 모델은 `PlayerWeapon` 이 자기 `OnEnable`/`OnDisable` 에서 켜고 끈다. 장착
상태와 화면의 총이 어긋날 자리를 만들지 않으려는 것이다.

**손전등 · 권총 · 산탄총은 셋 다 「주워야 쓴다」.** 각자 `IsOwned` 를 갖고
`PickUp()` 으로 켜진다. 안 주운 총은 `Equip` 이 거부하고, 안 주운 손전등은 `F` 를
눌러도 반응하지 않는다. 프리팹 기본값은 **전부 미획득**이라 C 의 장 씬에 그대로
놓으면 기획대로 맨손으로 시작한다.

셋을 같은 모양으로 맞춘 이유는, 손전등만 다르게 두면 「가졌는가」를 다루는 방식이
두 벌이 되기 때문이다. 나중에 세 번째 획득물이 생겨도 같은 자리에 붙는다.

**탄약은 탄창(`Loaded`)과 여분(`Reserve`)으로 나뉜다.** 획득물은 여분에 넣고,
재장전이 여분에서 탄창으로 옮긴다. 재장전 중에는 쏘지 못하고, 무기를 바꾸거나
무거운 것을 들면 `OnDisable` 에서 취소된다 — 다시 들면 처음부터다.

재장전 동작은 애니메이션이 아니라 **총 모델 전체를 내렸다 올리는 것**이다. 뼈대가
없어서 그렇게 했고, `sin` 곡선이라 시작과 끝이 정확히 원래 자세라 튀지 않는다.
모델이 붙으면 여기를 애니메이터로 갈아끼운다.

`PlayerHud` 는 `HealthChanged` · `AmmoChanged` · `ReloadingChanged` · `Equipped` ·
`StaminaChanged` 를 구독한다. 무기를 바꾸면 이전 무기의 구독을 끊는다 — 안 끊으면
안 든 총의 탄약이 화면에 남는다. 초기값은 `OnEnable` 이 아니라 `Start` 에서 읽는다.
`OnEnable` 은 `PlayerHealth.Awake` 보다 먼저 돌 수 있어 체력을 0 으로 읽는다.

**전부 이벤트로 받지는 않는다.** 배터리 잔량과 조준 대상은 매 프레임 바뀌므로
이벤트로 만들어도 매 프레임 오고, 대신 구독·해지 자리만 늘어난다. 이 둘은
`Update` 에서 `Flashlight.BatteryRatio` 와 `PlayerInteractor.Prompt` 를 그냥 읽는다.
기준은 「자주 바뀌는가」가 아니라 **「HUD 가 안 볼 때도 바뀌는가」**다 — 체력과
탄약은 화면 밖 사건이라 이벤트고, 이 둘은 아니다.

표시 규칙(불투명도 · 경고 문턱 · 점멸)은 [`../ui-assets/README.md`](../ui-assets/README.md)
의 「HUD 동작 제안」 표를 바탕으로 하고, 값은 `PlayerHud` 상단에 상수로 모아 두었다.
스프라이트는 B 가 만든 `Assets/Game/UI/Art/` 를 쓴다. 표에서 벗어난 곳은 두 군데이고
이유는 [`decisions.md`](decisions.md) 에 있다 — 스태미너 · 배터리를 늘 띄우는 것과
불투명도를 올린 것이다.

IMPORTANT: **HUD 요소는 스프라이트 원본 크기에 맞춰 그린다.** 1920×1080 기준 캔버스에서
원본 픽셀과 화면 픽셀이 1:1 로 맞아야 선이 안 뭉갠다. 처음에 절반 크기로 그렸다가
「해상도가 떨어져 보인다」는 지적을 받았다. 압축 문제가 아니었다 — 전부 `RGBA32`
무압축인데도 축소 자체로 흐려진 것이다. 게이지 두 종은 B 의 시안에 맞춰 0.75 배로
두었고, 나머지는 원본 크기 그대로다.

IMPORTANT: **프레임 스프라이트의 내부 창은 프레임 중앙이 아니다.** `battery-frame.png`
는 512×145 인데 창이 x 56~440 이라 중심이 8px 왼쪽이다. 채움을 정중앙에 두면 100% 일 때
오른쪽 테두리를 넘는다. `Battery/Fill` 의 `anchoredPosition.x` 가 `-6` 인 이유다
(네이티브 −8 × 0.75). 프레임을 갈아끼우면 알파를 다시 떠서 창 위치를 재야 한다.

에디터 게임 뷰가 1920 보다 작으면 `CanvasScaler` 가 그만큼 줄인다. 1044×485 에서는
0.494 배라 실제 빌드의 절반 크기로 보인다. **HUD 의 크기와 선명도는 게임 뷰를
1920×1080 으로 두고 판단한다.**

IMPORTANT: **HUD 문구는 영문이다.** 기본 폰트에 한글 글리프가 없어 WebGL 빌드에서
깨진다. 에디터에서는 시스템 폰트로 대체되어 멀쩡해 보이고, `Font.GetCharacterInfo`
도 한글이 있다고 답하므로 **에디터에서는 확인할 수 없는 종류다.** 근거는
[`decisions.md`](decisions.md) 의 「UI 는 uGUI 로 만들고 화면 문구는 영문으로 쓴다」.

IMPORTANT: 이 제약은 **`IInteractable.Prompt` 에도 걸린다.** 그 문구는 상호작용
담당(C)이 정하고 HUD 는 받아서 찍기만 하는데, 한글이면 화면에서 깨지는 것은 여기다.
지금 있는 `Lever` 는 `Pull lever` 라 문제가 없다.

**발소리는 시간이 아니라 이동 거리로 낸다.** `PlayerFootsteps` 가 수평 이동을 쌓다가
보폭을 넘으면 한 번 낸다. 걷기 · 달리기 · 웅크리기의 간격이 속도에서 저절로 따라오고,
벽에 붙어 제자리걸음 할 때 소리가 나지 않는다. 타이머로 하면 속도를 고칠 때마다 간격도
같이 고쳐야 한다. 떠 있는 동안은 쌓지 않는다 — 쌓으면 착지하자마자 한 걸음이 터진다.

### 소지품은 장을 넘어 따라간다

장마다 `Player` 가 새로 생기므로, 1 장에서 주운 손전등은 2 장이 열리는 순간
사라진다. 씬에 놓인 프리팹이 `Awake` 에서 인스펙터 기본값으로 자기를 초기화하기
때문이다. `GameFlow` 가 나갈 때 베껴 두고 들어와서 되돌린다.

| 무엇 | 어디에 |
| --- | --- |
| 베끼는 것 | 손전등 소지 · 남은 배터리(초) · 무기별 소지 · 탄창 · 여분 · 장착한 무기 |
| 베끼는 시점 | `GameFlow.LoadChapter` — **장 이름이 바뀔 때만** |
| 되돌리는 시점 | `GameFlow.EnterChapter` (`sceneLoaded`) |
| 담는 그릇 | `Progress/PlayerLoadout` |

**같은 장을 다시 시작할 때는 베끼지 않는다.** 그래야 보관된 것이 장 시작 시점의
것으로 남아, 죽으면 그 장을 시작할 때 가졌던 만큼으로 돌아간다. 죽기 직전을
베끼면 배터리와 탄약이 죽을 때마다 되살아나 **죽어서 보충하기**가 된다.

IMPORTANT: 되돌리기는 `PickUp` · `AddBattery` · `AddAmmo` 로 할 수 없다. 셋 다
**더하는** 함수인데 필요한 것은 **맞추는** 것이다. 그래서 `Flashlight.RestoreState`
와 `PlayerWeapon.RestoreState` 를 따로 두었다. 이 둘은 진행 시스템이 부르는
입구이고 게임 로직에서 부르지 않는다.

IMPORTANT: 소지 항목을 늘리면 `PlayerLoadout` 의 `Capture` 와 `Apply` **양쪽**에
넣는다. 한쪽만 고치면 조용히 안 넘어가고, 증상이 「가끔 사라진다」라 원인을
찾기 어렵다.

되돌리는 시점이 `sceneLoaded` 인 것은 플레이어의 초기화가 전부 `Awake` 에 있기
때문이다(배터리 · 탄약 · 시작 무기 장착). 초기화가 `Start` 로 옮겨가면 이 시점이
무효가 되니 한 프레임 뒤로 미뤄야 한다.

### 플레이어가 내는 소리는 `PlayerMotor` 가 낸다

`PlayerMotor.NoiseRadius` — 지금 내는 소리가 닿는 거리(m)다. 서 있으면 0, 웅크려
걸으면 4, 걸으면 9, 달리면 16 이다. **적은 이 값을 읽어 자기와의 거리와 비교만 한다.**

| 부르는 쪽 | 무엇 |
| --- | --- |
| 적 (B) | `PlayerMotor.NoiseRadius` 를 읽어 청각 판정 |

**2026-08-09 · 이 계약은 이제 둘 다 지킨다.** 하루 동안 `Crawler` 가 자기 안에서
`hearRange`(13m) · `hearSpeed`(2.6)로 다시 만들어 두 벌이었는데, A 가 6 장을
붙이다 발견해 알려 주었고 B 가 **소음 반경 쪽으로 통일**했다. 위 표를 사실로
읽어도 된다.

크기는 이 값으로 통일하되 **반응은 적마다 다르다.** `Colossus` 는 듣고 바로
추격하지만 `Crawler` 는 `Investigate` 로 가서 확인한다. 통일한 것은 「얼마나
멀리 들리는가」이고, 「듣고 무엇을 하는가」는 적의 성격이다. 적마다
`hearingScale` 로 예민함만 조절한다.

IMPORTANT: **청각은 벽을 통과한다.** 시야와 다른 점이 이것이고, 「보이지 않는 곳에
있으면 안전하다」를 깨는 것이 이 값이 있는 이유다. 여기에 레이캐스트를 걸면 청각이
시야의 복사본이 된다. 근거는 [`decisions.md`](decisions.md) 의 「적은 소리로도
알아챈다」.

`Shared/` 에 인터페이스를 두지 않은 이유는 소리를 내는 것이 지금 플레이어뿐이라
합의할 것이 없기 때문이다. 적이 서로 소리를 듣게 되면 그때 올린다.

**점프와 착지도 같은 클립을 쓴다.** 새 클립을 뽑지 않았다. 발이 바닥을 미는 소리는
밟는 소리와 같은 재질에서 나므로, **도약은 피치를 내리고 음량을 줄여** 「밟았다」를
「밀었다」로 바꾼다. 착지는 반대로 음량을 올린다. 표면이 바뀌면 둘 다 저절로
따라오고, 표면마다 점프음을 따로 준비하지 않아도 된다.

IMPORTANT: **도약은 밖에서 알 수 없다.** 착지는 접지 상태가 바뀌는 것으로 알 수
있지만, 점프 입력은 `PlayerMotor` 안에서만 읽고 웅크림·접지 조건을 통과한 뒤에야
실제로 뜬다. 그래서 `PlayerMotor.Jumped` 이벤트를 두었다.

IMPORTANT: **`CharacterController` 가 꺼져 있으면 걷지 않는 것으로 본다.** 삭도에
올라타면 콜라이더를 끄고 플레이어를 차체에 붙여 옮기는데, 그 이동이 그대로 쌓이면
가만히 서서 걷는 소리가 난다. 태우는 쪽마다 발소리를 따로 꺼주게 하지 않고
`PlayerFootsteps` 에서 한 번 막는다. 앞으로 승강기나 연출로 플레이어를 실어 나를 때도
같은 자리에서 처리된다.

IMPORTANT: **밟고 있는 바닥이 무엇인지는 레벨을 만든 쪽만 안다.** 회색 박스에는 재질이
없으므로 장마다 기본 표면 하나를 정하고, 씬에 놓인 `Player` 인스턴스에서
`PlayerFootsteps.surface` 를 덮어쓴다. 처음부터 표면 판정을 만들면 회색 박스에 쓸 데가
없다. 한 장 안에서 갈라야 할 때가 오면 그때 만든다.

| 장 | 표면 | |
| --- | --- | --- |
| 1장 관제동 | `Concrete` | 프리팹 기본값이라 손댈 것이 없다 |
| 2장 숙소동 | `Wood` | **씬에서 바꿔야 한다** |
| 6장 승강장 | `MetalGrate` | ✅ |
| 5장 외부 철탑 | `Snow` | 그 장이 생길 때 |

IMPORTANT: `PlayerMotor` 에도 같은 것을 만들었다가 걷어냈다 (2026-08-09). 같은 날
두 사람이 각자 만들어 **발소리가 두 번 났다.** 발소리를 손볼 때는 `PlayerFootsteps`
하나만 본다. 근거는 [`decisions.md`](decisions.md) 의 「발소리는 `PlayerFootsteps`
하나로 간다」.

`TestDamageTarget` 과 `TestTarget.prefab` 은 **지웠다** (2026-08-08). A 가 B 의 적을
기다리지 않으려고 만든 사격 검증용 대역이었고, `1901d85` 에서 실제 `Crawler` 로
양방향 확인이 끝나 역할이 없어졌다. 만들 때 「`Crawler.prefab` 이 오면 지운다」고
적어둔 대로다.

입력을 한 곳으로 모은 이유는 **사망 처리 때문**이다. `PlayerHealth` 가 죽을 때
`PlayerInputReader` 하나만 끄면 액션 맵이 꺼지고, 나머지 컴포넌트는 전부 0 을
읽는다. 각자 "죽었는지" 를 확인하는 분기를 두지 않아도 된다.

IMPORTANT: 입력 액션은 프리팹에 참조를 끼우지 않고 **프로젝트 전역 에셋**
(`InputSystem.actions`) 을 쓴다. 프리팹마다 끼우면 하나 빠뜨렸을 때 그 프리팹만
조용히 입력을 못 받는다.

### Enemy

`Assets/Game/Enemy/`. 1단계는 `Crawler` 하나다. 회색 박스이며 외형을 전혀 모른다 —
모델 파이프라인이 늦어져도 1단계가 멈추지 않도록 나중에 자식으로 끼운다.

**Enemy 는 Player 의 코드를 하나도 참조하지 않는다.** 접점이 셋뿐이고 전부 공용
계약이라, A 가 무엇을 어떻게 만들든 B 는 영향을 받지 않는다.

| 접점 | 무엇 |
| --- | --- |
| `Player` 태그 | 추격 대상을 `FindWithTag` 로 찾는다. 매 프레임이 아니라 놓쳤을 때만 다시 찾으므로 늦게 스폰돼도 붙는다 |
| `IDamageable` | 적이 플레이어를 때리는 것과 총이 적을 죽이는 것이 같은 호출이다 |
| `GameLayers.EnemySight` | 시야 레이캐스트. 맨 앞에 맞은 것이 플레이어여야 본 것으로 친다 |

플레이어 참조가 없어도 예외 없이 대기하다 생기면 붙는다. `Player.prefab` 이 오기
전에도 태그만 붙인 캡슐로 검증할 수 있게 한 것이다.

등 뒤에서 맞으면 추격을 시작한다. 안 그러면 뒤에서 쏘는 것이 무위험 행동이 되어
기획의 「빠르지만 약하다」가 성립하지 않는다.

#### `Colossus` — 죽지 않는다

`Crawler` 와 코드를 공유하지 않는다. **규칙이 반대**이기 때문이다. `IsAlive` 가
언제나 참이고 `Death` 클립도 만들지 않는다. 체력을 아주 크게 주는 방식을 쓰지
않은 이유는, 큰 값은 언젠가 깎이기 때문이다. 탄약을 다 쓰면 죽는 적이 되는 순간
「죽지 않는 것이 있다」가 1장부터 6장까지 유지되지 않는다.

총이 만드는 유일한 효과는 **밀려남**이다. 누적 피해가 임계에 닿으면 뒤로 2.5m
밀려나 잠시 멈춘다. 밀려나 있는 동안 맞은 것은 다음 밀림에 쌓지 않는다 — 안 그러면
탄약만 있으면 영구히 묶어둘 수 있어 「도망친다」가 성립하지 않는다.

IMPORTANT: **총폭 3.44m 다. 이 적이 지나갈 통로는 4m 이상이어야 한다.** 6장을
만드는 A 가 레벨을 잡기 전에 알아야 하는 수치다. 좁으면 벽에 끼어 안 온다.

IMPORTANT: 크기를 **Transform 스케일로 만들지 않는다.** 스케일을 쓰면
`NavMeshAgent` 반경과 물리가 어긋난다. 실측 크기로 만든다.

### Interaction

`Assets/Game/Interaction/`. 넷이고 전부 `IInteractable` 이다.

| 컴포넌트 | 무엇 | 레이어 |
| --- | --- | --- |
| `Lever` | 장치를 발동시키는 손잡이 | `Interactable`(16) |
| `Carriable` | 두 손으로 드는 물건. 들면 총을 못 쓴다 | `Carriable`(17) |
| `CarrySlot` | 운반물을 받는 자리. 받으면 장치가 발동한다 | `Device`(18) |
| `Pickup` | 주우면 무언가를 주는 물건 | `Interactable`(16) |
| `Readable` | 읽을거리. 무전 일지 · 근무표 · 낙서 | `Interactable`(16) |

#### Lever

**레버는 조작부일 뿐이고 무슨 일이 일어나는지는 장치가 정한다.** `devices` 에 넣은
`Device` 들을 발동시킨다. 1단계에는 여는 대상을 직접 들고 있었는데, 장치 시스템이
없을 때 미리 추상화하면 상상으로 만들게 되기 때문이었다. 실물이 생겨 갈아끼웠다.

`oneShot` 이 두 가지 물건을 만든다.

| `oneShot` | 무엇이 되나 | 눌렀을 때 |
| --- | --- | --- |
| 켬 (기본) | **한 번 당기는 레버.** 셔터 · 삭도 | `Activate`. 내려간 채로 남고 다시 안 눌린다 |
| 끔 | **켜고 끄는 스위치.** 서치라이트 | `Activate` / `Deactivate` 를 번갈아. 각도도 왕복한다 |

IMPORTANT: **각도가 되돌아오는 것은 「다시 당길 수 있다」는 뜻이다.** `oneShot`
레버를 되돌리는 연출을 만들었다가 걷어낸 적이 있다. 올라와 있는데 안 눌리면 색이
아무리 달라도 플레이어는 계속 눌러본다. 문구도 같다 — `promptWhenOn` 은 스위치일
때만 채운다.

#### Carriable

기획이 늘린 규칙은 이것 하나다 — 「무거운 것을 들면 총을 못 쓴다」. 연료통과 축전지가
이 컴포넌트다.

들면 눈(`MainCamera` 태그가 붙은 카메라)에 붙고 콜라이더가 꺼진다. 총을 잠그는 것은
`WeaponSwitcher.SetCarrying(true)` 이고, 내려놓으면 들고 있던 총으로 돌아온다.

IMPORTANT: **내려놓기는 조준한 것이 없을 때만 걸린다.** 들고 있는 동안에도 다른 것과
상호작용할 수 있어야 하기 때문이다 — 6장에서 연료통을 들고 권양기 앞에 서서 누르는
것이 그 자리다. 같은 `E` 를 나눠 쓰되 **조준한 것이 있으면 그쪽이 먼저**고, 허공을
보고 눌렀을 때만 내려놓는다. 장치가 운반물을 받을 때는 `Carriable.Drop()` 을 바깥에서
부른다.

#### CarrySlot

`Carriable` 만으로는 「들고 다닌다」에서 끝난다. **어디에 놓아야 의미가 생기는지**를
정하는 것이 이쪽이고, 그래서 받을 물건(`accepts`)과 발동시킬 장치(`devices`)를 둘 다
여기서 지정한다. 6장 권양기의 연료 투입구가 첫 용도다.

받은 물건은 기본적으로 **사라진다.** 연료는 부으면 없어지는 것이고, 남겨두면 다시
집어 다른 데로 옮길 수 있다. 남겨야 하면 `consume` 을 끄고 `placeAt` 을 준다.

IMPORTANT: **빈손이면 아예 안 잡힌다.** 「E 를 눌렀는데 아무 일도 안 일어났다」가
가장 나쁜 피드백이라서다. 무엇이 필요한지 알려 줘야 하는 자리만 `promptWhenEmpty` 를
채운다 — 그때는 문구만 뜨고 눌러도 아무 일이 없다는 것을 알고 쓴다.

#### Pickup

주우면 플레이어에게 무언가를 준다. **획득물마다 클래스를 만들지 않는다** — 종류의
차이는 A 의 어느 함수를 부르는가뿐이다.

| `kind` | 부르는 것 | `amount` |
| --- | --- | --- |
| `Flashlight` | `Flashlight.PickUp()` | 안 봄 |
| `Battery` | `Flashlight.AddBattery(초)` | **초** |
| `Pistol` · `Shotgun` | `WeaponSwitcher.PickUp(종류)` | 안 봄 |
| `PistolAmmo` · `ShotgunAmmo` | `WeaponSwitcher.AddAmmo(종류, 발수)` | **발수** |

**총과 탄약은 따로다.** 총을 안 주웠어도 탄약은 쌓이므로 「탄약만 먼저 발견」 같은
배치가 된다. 탄약이 가득 차 한 발도 안 들어가면 **획득물이 사라지지 않는다.** 쓰고
와서 다시 주우면 된다.

#### Readable

`title` 과 `body` 를 넣으면 <b>E</b> 로 펼쳐 읽는다. 그리는 곳은
[`ReadingPanel`](#ui) 이고, 같은 키로 닫는다.

**읽는 동안 플레이어를 묶지 않는다.** 움직임을 막으면 그 순간이 컷신이 되는데, 이
게임에서 조작을 빼앗는 자리는 6장 하나로 충분하다.

IMPORTANT: **책상에 놓인 종이는 콜라이더를 따로 키운다.** 눈높이가 `1.65` 인데 책상
위 종이는 `1.0` 근처라 광선이 위로 지나간다. 보이는 두께는 그대로 두고 콜라이더의
`size.y` 만 키워 눈높이를 지나게 하되, **반드시 `isTrigger` 로 둔다.** 안 그러면
보이지 않는 벽이 생겨 플레이어가 책상 앞에서 걸린다. 벽에 붙는 근무표는 원래
눈높이라 이럴 필요가 없다.

#### 놓을 때 지킬 것

IMPORTANT: **상호작용 대상은 눈높이에 둔다.** A 의 조준 광선은 카메라에서 나가고
서 있을 때 눈높이는 바닥에서 **`y = 1.65`** 다(실측). 허리 높이에 두면 광선이 위로
지나가 아무리 가까이 가도 안 잡힌다. **콜라이더 세로 범위가 그 높이를 지나야 한다** —
윗면이 `1.60` 이면 5cm 차이로 안 잡히고, 증상은 「상호작용이 고장났다」로 보인다.
받침대 윗면을 `1.40` 쯤에 두고 그 위에 올리면 된다.

IMPORTANT: **동선 위에 두지 않는다.** 상호작용 대상은 보통 막는 콜라이더라
통로 한가운데 두면 플레이어가 거기서 걸린다. 6장 레버를 출구 통로(`x -3~3`)
바깥인 `x=4` 에 둔 것이 그 이유다.

IMPORTANT: **`RequireComponent` 에 `Collider` 를 적지 않는다.** 추상 클래스라 Unity 가
붙이지 못하고 `AddComponent` 가 **조용히 `null` 을 돌려준다.** 빈 오브젝트에 컴포넌트를
붙일 때 그대로 밟는다. `BoxCollider` 처럼 구체 타입을 적는다.

### Devices

`Assets/Game/Devices/`. 기획의 장치는 아홉이지만 **구현은 세 개다.** 셋 다
`Device` 를 물려받고 `IDeviceTrigger` 로 발동을 받는다.

| 컴포넌트 | 언제 켜지나 | 끌 수 있나 | 기획의 어느 장치 |
| --- | --- | --- | --- |
| `InstantDevice` | 바로 | 아니오 | 셔터 · 연료 인화 · 수소 폭발 · 제설포 |
| `TimedDevice` | `seconds` 뒤 | 아니오 | 히터 케이블 · 환기 팬 · 발전기 예열 |
| `SustainedDevice` | 바로 | **예** | 서치라이트 · 유도등 · 로터리 제설기 |

셋의 차이는 **언제 `IsActive` 가 되고 되돌릴 수 있는가**뿐이다. 「무엇이
일어나는가」는 전부 `Device` 가 맡는다.

| 인스펙터 | 무엇 |
| --- | --- |
| `enables` | 발동하면 켜질 것들. 내려온 셔터, 열린 문 |
| `disables` | 발동하면 꺼질 것들. 얼음 막, 막고 있던 벽 |
| `activated` · `deactivated` | 소리와 연출을 끌어다 놓는 자리 |

코드에서 상태를 따라가야 하면 `Device.ActiveChanged` 를 구독한다. 인스펙터의
`UnityEvent` 와 나란히 둔 것은 **배선 비용이 다르기 때문**이다. 소리 하나는
에디터에서 끌어다 놓는 편이 빠르고, 시스템이 상태를 물고 가는 것은 코드가 안전하다.

`TimedDevice` 는 `IsRunning` · `Progress` · `SecondsLeft` 를 내놓는다. 2장에서
히터가 도는 동안 숨는 구간과 4장 환기 팬 대기가 이 값을 본다. **한 번 걸면 못
멈춘다** — 취소를 만들면 기다리는 것이 선택이 되어 버티는 구간 자체가 사라진다.
4장의 「환기 팬을 돌릴까 그냥 들어갈까」도 **걸기 전에** 하는 선택이다.

IMPORTANT: **`Device.Awake` 가 시작 모습을 강제로 맞춘다.** `enables` 를 끄고
`disables` 를 켠다. 편집하다 켜둔 채 저장하는 일은 반드시 생기고, 그것을 씬 파일에
맡기면 「내 컴퓨터에서는 닫혀 있었다」가 된다.

`PassBy` 는 장치가 아니라 **장치의 결과**다. 켜지면 한 번 지나가고 스스로 꺼진다.
1장 옥상에서 능선을 건너가는 실루엣이 첫 용도이고, 장치의 `enables` 에 넣으면
켜지는 순간 저절로 지나간다.

`animator` 를 물리면 지나가는 동안 속도 파라미터를 올린다. **위치만 옮기면 미끄러져
지나가고, 그러면 「지나갔다」가 아니라 「무언가 흘러갔다」로 읽힌다.** 1장 실루엣은
진짜 `Colossus` 프리팹이고 `Speed` 를 1.15 로 올려 너클보행을 돌린다. 적으로 쓰지
않으므로 `Colossus` · `NavMeshAgent` · `CapsuleCollider` 를 꺼 두고 어두운
머티리얼로 덮는다.

**한 레버로 성격이 다른 장치를 함께 밀 수 있다.** 1장이 그 예다 — 서치라이트
스위치가 `SustainedDevice`(빛)와 `InstantDevice`(출구)를 같이 발동시킨다. 스위치를
다시 끄면 빛은 꺼지지만 **출구는 열린 채로 남는다.** 즉시 발동 장치가 `Deactivate`
를 무시하기 때문이고, 「한 번 본 것은 되돌릴 수 없다」가 그대로 코드가 된다.

### Progress

| 파일 | 하는 일 |
| --- | --- |
| `Chapters` | 장 씬 이름과 진행 순서. **장을 추가할 때 고칠 곳은 여기 하나다** |
| `GameFlow` | 장 전환 · 재시작 · 체크포인트 보관 · 죽음 구독. 게임에 하나 |
| `SpawnPoint` | 장이 시작될 때 플레이어가 서는 자리 |
| `Checkpoint` | 지나가면 다시 시작할 자리가 바뀐다 |
| `ChapterExit` | 장의 끝. 들어오면 다음 장으로 |

`GameFlow` 는 **씬에 배치하지 않는다.** 첫 접근 때 스스로 생기고 씬이 바뀌어도
살아남는다. 씬에 두면 세 장 모두에 같은 오브젝트를 넣어야 하고, 고칠 일이 생길
때마다 병합할 수 없는 파일을 세 개씩 건드리게 된다.

다음 장이 어디인지는 `Chapters.Order` 만 안다. `ChapterExit` 에 다음 장 이름을
적지 않는 이유는, 적어두면 3 · 4 · 5 를 끼워 넣을 때 씬을 열어 고쳐야 하기
때문이다.

### UI

`Assets/Game/UI/`. HUD 는 A 의 `Player.prefab` 안에 있고, 여기 있는 것은 화면 단위로
뜨는 것들이다.

| 파일 | 하는 일 |
| --- | --- |
| `TitleScreen` | 타이틀. 「시작」이 `GameFlow.StartNewGame()` 을 부른다 |
| `EndingScreen` | 엔딩. 「돌아가기」가 `GameFlow.ReturnToTitle()` 을 부른다 |
| `ReadingPanel` | 읽을거리를 펼쳐 보여준다. `Readable` 이 부른다 |

`ReadingPanel` 은 **씬에 배치하지 않고 처음 필요할 때 스스로 생긴다.** 캔버스와
글자를 코드로 세운다. 장마다 캔버스를 넣으면 병합할 수 없는 파일을 장 수만큼
건드리게 되고, 문구 하나 고칠 때 그 전부를 다시 열어야 한다. `GameFlow` 를 씬에 두지
않은 것과 같은 판단이다.

폰트는 `TMP_Settings.defaultFontAsset` 을 그대로 쓴다. 프로젝트 기본 폰트가 한글
폰트(`IBMPlexSansKR-Regular SDF`)라 따로 참조를 들 필요가 없고, 폰트를 바꿀 때 고칠
곳이 프로젝트 설정 한 군데로 남는다.

IMPORTANT: **아틀라스는 Dynamic 이다.** 개발 중에는 문구가 계속 바뀌어 정적으로
구우면 글자 하나 고칠 때마다 다시 구워야 한다. WebGL 은 빌드 용량이 곧 첫 로딩
시간이므로 **배포 전에 실제 쓰는 글자만 Static 으로 다시 굽는다.**

## 시스템 간 관계

지금 존재하는 관계는 이것뿐이다. 시스템이 들어올 때마다 여기에 더한다.

```
PlayerWeapon ──레이캐스트(Shot)──▶ IDamageable   (적: B)
PlayerInteractor ──레이캐스트(Interaction)──▶ IInteractable   (문·레버: C)
Lever ──Activate/Deactivate──▶ Device   (장치: C)
Carriable ──SetCarrying──▶ WeaponSwitcher   (무기: A)
Pickup ──PickUp/AddAmmo/AddBattery──▶ WeaponSwitcher · Flashlight   (A)
Enemy ──▶ IDamageable   (PlayerHealth: A)
PlayerHealth ──Died 이벤트──▶ 재시작   (Progress: C, 아직 구독자 없음)
```

**Player 는 Enemy 와 Interaction 의 타입을 하나도 모른다.** 전부
`Shared/` 의 인터페이스를 통해서만 닿는다. 그래서 A 는 B 와 C 의 구현을 기다리지
않고, 반대로 B 와 C 도 A 를 기다리지 않는다.

바깥에서 Player 를 부르는 자리는 아래 셋이다. 다른 곳에서 부를 일이 생기면 여기에
적고 나서 부른다.

| 부르는 쪽 | 무엇 |
| --- | --- |
| 적 (B) | `PlayerHealth.TakeDamage` |
| 획득물 (C) | `WeaponSwitcher.AddAmmo(종류, 발수)` — **여분에 들어간다** · `Flashlight.AddBattery` |
| 총 획득 (C) | `WeaponSwitcher.PickUp(종류)` — 권총 3장, 산탄총 5장 |
| 손전등 획득 (C) | `Flashlight.PickUp()` — 1장 |
| 양손 운반 (C) | `WeaponSwitcher.SetCarrying(true/false)` |
| 진행 (C) | `PlayerHealth.Died` 구독, 장 전환 시 `PlayerHealth.Restore` |

`PlayerMotor` 는 구독할 것도 셋 낸다 — `StaminaChanged` · `RecoveryLockChanged` ·
`Jumped`. 앞 둘은 HUD 가 쓰고 `Jumped` 는 발소리가 쓴다. 점프에 연출을 붙일 일이
생기면 이 이벤트를 쓴다.

IMPORTANT: 「무거운 것을 들면 총을 못 쓴다」 는 **운반 쪽이 총을 끄는 것이 아니라**
`SetCarrying` 을 부르는 것으로 한다. 내려놓으면 들고 있던 총으로 알아서 돌아오므로
운반 쪽이 무엇을 들고 있었는지 기억하지 않아도 된다.

**의존은 한 방향이다.** `Progress` 가 `Player` 를 찾아가고, `Player` 는
`Progress` 를 모른다. 그래야 A 가 자기 작업만으로 완결된다.

```
Progress ──찾는다──▶ "Player" 태그        (GameObject.FindWithTag)
Progress ──구독──▶ PlayerHealth.Died      (죽었을 때 재시작)
Progress ──옮긴다──▶ CharacterController  (스폰 · 체크포인트로 순간이동)
```

`GameFlow` 는 장이 로드될 때마다 그 씬의 `PlayerHealth` 를 찾아 `Died` 를 다시
건다. 씬이 바뀌면 `PlayerHealth` 도 새로 생기기 때문이다.

IMPORTANT: **첫 씬에는 `sceneLoaded` 가 오지 않는다.** 씬이 먼저 로드되고 그 뒤에
`GameFlow` 가 생기기 때문이다. 그래서 `RuntimeInitializeOnLoadMethod` 로 시작
시점에 한 번 더 붙인다. 이것이 없으면 **빌드의 첫 장에서 죽어도 재시작이 걸리지
않는다.** 씬 전환으로 들어온 장에서는 멀쩡해서, 관통 테스트만으로는 안 잡힌다.

한동안은 매 프레임 `IDamageable.IsAlive` 를 보는 방식이었다. A 의 구현을 기다리지
않으려고 쓴 임시 방편이었고, `Died` 가 생기면서 걷어냈다. 그 폴링을 담고 있던
`PlayerDeathWatcher` 와 씬마다 두던 `[Progress]` 오브젝트도 함께 사라졌다.

IMPORTANT: `CharacterController` 가 붙은 오브젝트는 `transform` 만 옮기면 다음
프레임에 되돌아온다. 컨트롤러를 껐다 옮기고 다시 켜야 한다. `GameFlow.Teleport`
가 그렇게 한다.

### 장 씬에 두는 것

`Ch1` · `Ch2` · `Ch6` 이 이 구성이다.

| 오브젝트 | 무엇 |

진행용 오브젝트를 따로 두지 않는다. `GameFlow` 는 스스로 생기고 죽음 구독도
자기가 한다.
