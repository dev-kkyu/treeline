# 게임 기술 결정 기록

무엇을 택했는지가 아니라 **왜 그렇게 택했는지**를 남기는 문서다. 코드는 결과만
보여주기 때문에, 이유가 사라지면 이미 버린 대안을 다시 검토하게 된다.

**게임 자체의 기술**만 다룬다. Claude Code 환경 구성은
[`docs/ai/setup.md`](../ai/setup.md) 로, 게임 기획은
[`docs/game-design/decisions.md`](../game-design/decisions.md) 로 분리했다.

## 쓰는 법

새 항목을 **위쪽에** 추가한다.

```markdown
## YYYY-MM-DD · <결정을 한 줄로>

<판단 근거. 무엇을 택했는지보다 왜가 중요하다.>

버린 안: <검토했으나 택하지 않은 것과 그 이유>
```

구조를 바꾸는 변경이라면 이 기록과 코드를 **같은 커밋**에 담는다. 따로 미루면
반드시 어긋나고, 어긋난 기술 문서는 없는 것보다 나쁘다.

## 2026-08-08 · 입력은 `PlayerInputReader` 한 곳에서만 읽는다

플레이어 컴포넌트가 각자 `InputAction` 을 들고 있으면, 사망했을 때 이동 · 사격 ·
상호작용에 **전부 "죽었으면 그만둔다" 분기를 넣어야 한다.** 하나 빠뜨리면 시체가
문을 여는 버그가 되고, 그런 버그는 늦게 발견된다.

입력을 한 컴포넌트로 모으니 `PlayerHealth` 가 사망 시 그것 하나만 끄면 된다.
액션 맵이 꺼지면서 나머지는 전부 0 을 읽으므로 분기 자체가 없어진다.

액션 에셋은 프리팹에 참조를 끼우지 않고 **프로젝트 전역 에셋**
(`InputSystem.actions`) 을 쓴다. Unity 6 템플릿이 이미
`Assets/InputSystem_Actions.inputactions` 를 전역으로 지정해 둔 것을 그대로 쓴다.

버린 안: 컴포넌트마다 `[SerializeField] InputActionAsset`. 프리팹이 늘어날수록
끼우는 것을 하나 빠뜨리기 쉽고, 그러면 그 프리팹만 조용히 입력을 못 받는다.
증상이 "가끔 안 움직인다" 로 나와서 원인에 닿기까지 오래 걸린다.

버린 안: 액션 에셋의 C# 래퍼 생성(`generateWrapperCode`). 타입이 잡혀서 좋지만
생성 파일이 커밋에 섞이고, 새로 클론한 사람은 Unity 가 한 번 임포트하기 전까지
컴파일이 깨진다.

## 2026-08-08 · `Interact` 의 Hold 를 없애고 `Flashlight` 를 더했다

템플릿 기본값의 `Interact` 는 **Hold** 인터랙션이라 꾹 눌러야 발동한다. 이 게임의
상호작용은 문 · 레버 · 밸브처럼 즉발이고, 기획의 1장은 "걷고, 보고, 문을 여는 법을
익힌다" 가 전부다. 첫 문에서 눌러도 안 열리는 경험을 줄 이유가 없다.

`Flashlight`(`F`) 는 템플릿에 없어서 새로 넣었다. 손전등은 1장부터 나온다.

에셋의 소유자는 A 다. 액션을 더하거나 이름을 바꾸는 사람은 A 이고,
`PlayerInputReader` 의 문자열도 같은 커밋에서 고친다.

버린 안: Hold 를 유지하고 대신 문에 "누르고 있기" UI 를 붙이기. 규칙이 하나 늘고,
기획이 규칙 수를 줄이려고 애쓴 자리를 되돌린다.

## 2026-08-08 · 달리기 · 점프 · 웅크리기를 지금 넣지 않는다

템플릿 액션 에셋에 `Sprint` · `Jump` · `Crouch` 가 이미 있어 붙이는 데 드는 비용은
거의 없다. 그래서 오히려 명시해 둔다. **안 넣은 것은 잊어서가 아니다.**

기획의 무서움이 좁고 느린 이동에 기대고 있다. 달릴 수 있으면 추격이 안 무섭고,
뛸 수 있으면 회색 박스 레벨의 막힌 길을 넘어간다. 나중에 빼는 것이 지금 안 넣는
것보다 비싸다.

웅크리기는 2장 회피가 실제로 들어올 때 판단한다. 액션은 에셋에 남겨 둔다.

## 2026-08-08 · 프리팹 이름을 먼저 박고 껍데기를 선행 커밋한다

인터페이스 3종으로 코드는 서로를 안 기다리게 됐는데, **물건은 여전히 기다린다.**
B 의 적은 추격할 대상이 필요하고 C 의 관통 확인에는 Player 와 Enemy 가 둘 다
필요하다. 1단계에 남은 유일한 대기 관계다.

두 가지로 끊었다. 첫째, 남에게 넘기는 프리팹의 **경로와 이름을 지금 확정**했다.
프리팹 rename 은 참조가 걸린 뒤에 하면 비싸다. 둘째, **A 가 `Player.prefab` 을
완성 전에 올린다.** 캡슐에 `CharacterController` 와 `Player` 태그만 붙은
껍데기여도 B 와 C 는 자기 샌드박스에서 검증을 시작할 수 있다.

적 이름은 기획의 「기는 것 · 큰 것 · 매달린 것」을 `Crawler` · `Colossus` ·
`Clinger` 로 옮겼다. 1단계에 쓰는 것은 `Crawler` 하나지만 셋을 같이 정했다.
나중에 정하면 그때 또 합의를 잡아야 한다.

버린 안: 각자 편한 이름으로 만들고 통합할 때 맞추기. 통합 시점이 곧 마감이라
이름을 바꿀 여유가 없는 때다.

## 2026-08-08 · `SampleScene` 을 버리고 각자 샌드박스 씬을 갖는다

템플릿이 만들어 준 `Assets/Scenes/SampleScene.unity` 는 **소유자가 없는 공용
씬**이다. 그대로 두면 셋이 다 거기서 실험하게 되고, 그 순간 병합할 수 없는 파일을
세 사람이 동시에 고치는 상황이 된다. 씬 소유권 규칙을 정해놓고 정작 기본 씬이 그
규칙을 어기고 있는 셈이라 지웠다.

대신 `Assets/Game/_Sandbox/<이름>.unity` 를 세 개 만들었다. `SampleScene` 을
복제해서 만들었으므로 `Main Camera` · `Directional Light` · `Global Volume` 이 그대로
들어 있다. 빈 씬으로 만들면 각자 URP 볼륨을 다시 붙여야 한다.

빌드 씬 목록(`EditorBuildSettings.asset`)은 비웠다. 샌드박스는 빌드에 넣지 않고,
1단계에서 `Ch1` · `Ch2` · `Ch6` 이 생기면 그때 등록한다.

버린 안: `SampleScene` 을 `_Sandbox/` 로 옮겨 한 사람이 인수하기. 남은 두 사람은
어차피 새로 만들어야 해서 셋의 출발점이 달라진다.

## 2026-08-08 · 피해 정보를 인자가 아니라 구조체로 넘긴다

`IDamageable.TakeDamage` 는 `int` 하나가 아니라 `DamageInfo` 구조체를 받는다.
플레이어(A)와 적(B)이 **같은 인터페이스를 양쪽에서 구현**하기 때문이다.

나중에 넉백 세기나 피해 종류가 필요해졌을 때 인자를 늘리면 A 와 B 의 코드가 동시에
깨진다. 구조체에 필드를 더하는 것은 구현한 쪽을 고치지 않아도 된다. 지금 20 줄을
더 쓰고 그 위험을 없앴다.

버린 안: `void TakeDamage(int amount)`. 더 짧지만, 확장할 때 두 사람이 같은 시점에
코드를 고쳐야 해서 서로를 기다리게 된다. 인터페이스를 둔 목적 자체가 그것을 없애는
것이다.

## 2026-08-08 · 레이어를 미리 다 잡고 담당별로 번호 구간을 나눈다

씬만 병합이 안 되는 줄 알았는데 `ProjectSettings/` 아래에도 셋이 다 건드리는
파일이 있다. `TagManager.asset`(레이어 · 태그), `DynamicsManager.asset`(충돌
매트릭스), `EditorBuildSettings.asset`(씬 목록) 세 개다.

레이어가 그중 제일 위험하다. 씬과 프리팹에 이름이 아니라 **번호로** 저장되기
때문이다(`m_Layer: 8`). 셋이 각자 8 번에 다른 이름을 넣고 한쪽이 rebase 로 밀리면
오브젝트가 조용히 엉뚱한 레이어가 되고, 레이캐스트부터 어긋나기 시작한다. 컴파일도
되고 에러도 안 나서 원인을 찾기 어렵다.

그래서 작업을 시작하기 **전에** 쓸 레이어를 한 번에 확정하고 한 커밋으로 넣었다.
아직 안 쓰는 `ViewModel` · `Hazard` 까지 미리 잡은 것은, 나중에 추가하는 비용이
지금 잡아두는 비용보다 훨씬 크기 때문이다. 번호는 남아돈다(24 개 중 8 개 사용).

**담당별로 번호 구간을 나눈 것**이 이 결정의 핵심이다. A 8~11, B 12~15, C 16~23,
공용 24~31. 각자 자기 구간 안에서만 추가하면 셋이 동시에 레이어를 늘려도 번호가
겹치지 않는다. 표와 규칙은 [`architecture.md`](architecture.md) 에 있다.

레이캐스트 마스크도 함께 고정했다. 레이어를 나눠도 각자 다른 마스크를 쓰면 의미가
없어서다. 번호를 코드에 직접 쓰지 않도록 `Shared/GameLayers.cs` 에 상수로 두고,
그 파일과 `TagManager.asset` 은 항상 같은 커밋에 담는다.

버린 안:

- **필요할 때마다 각자 추가하기.** 가장 자연스럽지만 위에 적은 충돌이 정확히
  이 방식에서 난다. 게다가 손해가 며칠 뒤에 드러난다
- **태그도 함께 정의하기.** 태그는 문자열로 저장되어 번호 충돌이 없으므로 굳이
  미리 잡을 이유가 없다. Unity 빌트인 `Player` 하나로 충분하고, 태그를 늘리면
  오타가 컴파일을 통과해 런타임까지 간다
- **`Interactable` · `Carriable` · `Device` 를 한 레이어로 합치기.** 마스크로
  구분할 수는 있지만 물리 처리가 다르다. 합친 것을 나중에 쪼개려면 이미 배치된
  오브젝트를 전부 다시 지정해야 한다

## 2026-08-08 · 기믹보다 관통을 먼저 만든다

제출물 1번이 「플레이 가능한 빌드」다. 그것을 먼저 손에 쥐면 이후 작업이 「있는
것을 개선」이 되고, 못 쥐면 마지막까지 「없는 것을 만들기」로 남는다.

그래서 1·2·6 을 먼저 만든다는 기획의 순서는 그대로 두되, 그 안에서 기믹을 뒤로
민다. 1단계의 완료 기준은 **처음부터 끝까지 걸어서 엔딩에 도달하고 죽을 수도
있는 것**이다. 회색 박스여도 된다. 여기까지 되면 즉시 WebGL 로 빌드해 배포한다.
그 시점부터 제출 가능한 상태가 된다.

1단계에서 잘라낸 것: 산탄총, 배터리 소모, 양손 운반, 장치 9종, 적 2종, 천장 낙하.
2단계에서 1·2·6 에 기믹을 붙이고, 3단계에서 3·4·5 를 만든다. 5장 컷라인은 기획에
적힌 대로 유지한다.

버린 안: 기획 순서대로 장마다 기믹까지 완성해 나가기. 한 장이 완성도 높게 나오는
대신 마감까지 관통이 안 될 위험이 있다.

## 2026-08-08 · 회색 박스 세 장을 한 사람이 몰아서 만든다

1단계에서 A 는 플레이어와 전투, B 는 적, C 는 1·2·6 회색 박스와 진행을 맡는다.
각자 자기 장을 처음부터 만들면 더 병렬처럼 보이지만, 그러면 A 와 B 가 시스템과
레벨을 동시에 하게 되어 셋 다 반쯤 된 채로 1단계가 끝나지 않는다.

회색 박스는 큐브 배치라 싸고 시스템은 비싸다. 싼 것을 한 사람이 몰아서 하고 비싼
것을 둘이 나누는 편이 1단계를 가장 빨리 끝낸다. 덤으로 「처음부터 끝까지
걸어지는가」를 한 사람이 책임지게 되어 통합 담당이 생긴다.

2단계에서는 장을 한 명씩 인수한다. 회색 박스는 C 가 만들었지만 살을 붙이는 것은
각자다.

## 2026-08-08 · 씬은 한 사람만 만지고, 남에게는 프리팹으로 준다

`.unity` 와 `.prefab` 은 두 사람이 동시에 고치면 병합할 수 없다. 세 명이 붙는
이상 이것이 병렬 작업을 막는 유일한 구조적 장애물이다.

한 씬의 소유자를 한 명으로 두고, 다른 담당은 프리팹을 만들어 넘긴다. 적을
배치해야 하면 적 담당이 프리팹을 주고 레벨 담당이 자기 씬에 놓는다. 같은 파일을
두 사람이 건드릴 일이 구조적으로 생기지 않는다.

함께 붙는 지점은 인터페이스 세 개(`IInteractable`, `IDamageable`,
`IDeviceTrigger`)로 최소화했다. 이것만 고정되면 서로의 구현을 몰라도 각자
진행된다.

버린 안: 하나의 씬에서 함께 작업하고 충돌이 나면 그때 해결하기. Unity YAML 은
손으로 병합하면 조용히 깨지므로 사후 대응이 성립하지 않는다.
## 2026-08-08 · 저장소와 Unity 프로젝트 폴더를 `treeline` 으로 개명

기획이 `Treeline` 으로 확정되면서 `mutual-game` · `Mutual/` 이 옛 제목의
잔재가 됐다. 둘 다 사람이 보는 이름이라 미루면 계속 어긋난다.

**저장소 이름은 제출물의 일부다.** GitHub Pages 주소가
`dev-kkyu.github.io/<저장소>/` 라서 심사자가 누를 링크에 그대로 들어간다.
그래서 `treeline-game` 이 아니라 `treeline` 으로, 대문자 없이 갔다. Pages 경로는
대소문자를 구분하므로 `TreeLine` 이면 소문자로 접근했을 때 404 가 난다.

Unity 프로젝트 폴더도 `Treeline/` 으로 바꿨다. 아래 2026-08-05 항목에 적었듯이
이 폴더명이 곧 Unity Hub 에 뜨는 프로젝트 이름이라, 그때의 판단 근거가 그대로
개명의 이유가 됐다.

**표기는 `Treeline` 하나로 통일한다.** 저장소는 URL 이라 `treeline`, 나머지는
전부 `Treeline` 이다. 제품명(`productName`)도, 문서 본문도 같다.

처음에는 타이틀 표기를 따라 제품명과 문서를 `TREELINE` 대문자로 뒀다가 되돌렸다.
**대문자는 표기(表記)이지 이름이 아니다.** 타이틀 카드나 제출 PDF 표지에서
대문자로 보이고 싶으면 폰트와 CSS 로 만들면 되고, 그것이 표시 계층에서 할 일이다.
원문에 대문자를 박아 넣으면 저장소 · 폴더 · 설정 · 문서가 저마다 다른 철자를 갖게
되어 매번 "여기선 어떻게 쓰지" 를 묻게 된다. 600 줄짜리 기획 문서 본문에서 계속
대문자가 나오면 읽기도 피곤하다.

버린 제목 `MUTUAL` 은 기록에서 대문자로 남긴다. 그 초안이 스스로 그렇게 쓴
이름이라 그대로 두는 편이 맞다.

IMPORTANT: **팀원은 Unity Hub 에서 프로젝트를 목록에서 지우고 다시 추가해야
한다.** Hub 는 절대 경로를 기억하므로 옛 경로가 그대로 남는다. 로컬 remote 도
`git remote set-url origin git@github.com:dev-kkyu/treeline.git` 로 바꾼다.

버린 안: `treeline-game`(개인 계정 네임스페이스라 접미사로 구분할 이유가 없고
링크만 길어진다), `TreeLine`(Pages 경로 대소문자 문제), 폴더는 `Mutual/` 로
두고 제품명만 바꾸기(Unity Hub 목록에 계속 옛 이름이 뜬다. 세 명이 맞춰야 하는
작업이라 미룰수록 비싸진다)

## 2026-08-06 · WebGL 을 `gh-pages` 브랜치로 배포

빈 씬으로 배포 경로를 먼저 뚫었다. 게임을 다 만든 뒤에 배포가 막히면 손쓸 시간이
없기 때문이다. 실제로 배포 주소에서 로딩까지 확인했다. (당시 주소는
`dev-kkyu.github.io/mutual-game/` 였다. 2026-08-08 에 저장소를 `treeline` 으로
바꿔 지금은 `https://dev-kkyu.github.io/treeline/` 다)

세 가지 설정이 맞물려야 동작한다. 하나라도 빠지면 조용히 실패한다.

- **Decompression Fallback 켜기** (Player → Web → Publishing Settings).
  압축은 Brotli 인데, GitHub Pages 는 `.br` 파일에 `Content-Encoding` 헤더를
  붙여주지 않는다. 폴백이 없으면 브라우저가 압축을 풀지 못해 로딩이 멈춘다.
- **`.nojekyll` 을 브랜치 루트에 두기.** GitHub Pages 는 기본으로 Jekyll 처리를
  하면서 밑줄로 시작하는 파일을 무시한다. 빌드에 그런 파일이 섞이면 404 가 난다.
- **`.gitattributes` 에 `* -text`.** 줄바꿈 변환이 `.wasm` 이나 `.unityweb` 에
  닿으면 파일이 깨지는데, 증상만 봐서는 원인을 찾기 어렵다.

브랜치 이름을 `gh-pages` 로 한 덕에 Pages 설정이 자동으로 켜졌다. GitHub 이 이
이름을 특별 취급한다.

재배포는 빌드 산출물을 이 브랜치에 **일반 커밋으로 쌓는다.** 브랜치를 통째로
갈아끼우는 방식이 흔하지만 그건 force push 가 필요하고, 이 저장소에서는 훅으로
막혀 있다. 히스토리가 무거워지지만 이 기간에는 문제되지 않는다.

버린 안: GitHub Actions 로 빌드까지 자동화. Unity 라이선스를 CI 에 넣어야 해서
설정 비용이 크고, 짧은 기간에 얻을 이득이 작다.

## 2026-08-05 · Unity 프로젝트를 저장소 루트가 아닌 `Mutual/` 에 배치

루트에 두면 `Assets/`, `Library/`, `Temp/`, `obj/`, `*.sln` 이 `docs/` 와 섞여
탐색기에서 문서가 묻힌다. 이 저장소는 제출 문서 3종이 심사 대상이라 문서가
곁다리가 아니다.

폴더명을 `game` 이 아니라 `Mutual` 로 한 것은, 이 이름이 곧 Unity Hub 의 프로젝트
목록에 표시되기 때문이다. 빌드 제품명은 폴더명과 무관하게 Player 설정에서 정한다.

대가는 Unity Hub 에서 열 때 하위 폴더를 지정해야 한다는 것과, CI 를 붙이면
`projectPath` 를 명시해야 한다는 것 두 가지다. 둘 다 한 번씩만 치른다.

## 2026-08-05 · 제3자 에셋 원본을 저장소에서 제외

에셋스토어 표준 EULA 는 원본 재배포를 금지한다. 빌드 산출물에 굽는 것은 허용된
사용이므로, `Assets/ThirdParty/` 를 `.gitignore` 로 빼고 배포 빌드에만 포함한다.

Unity 는 에셋을 GUID 로 참조하고 그 GUID 는 `.unitypackage` 안의 `.meta` 에서
오므로, 팀원이 같은 에셋을 같은 버전으로 각자 임포트하면 씬 참조가 그대로
맞는다. 원본을 공유하지 않아도 깨지지 않는 이유다.

버린 안: Unity 에서 glTF 로 추출해 웹 네이티브로 개발. 포맷을 바꿔도 라이선스는
그대로라 재배포 문제가 오히려 악화되고, 머티리얼·셰이더 변환 손실이 있으며,
미숙한 툴체인을 둘 다 다뤄야 한다.

## 2026-08-05 · Unity 6.3 LTS + URP 로 WebGL 빌드

제출 조건상 PC 실행 파일이 금지되어 웹 또는 APK 만 가능하다. HDRP 는 WebGL 을
지원하지 않고, Built-In 은 새로 시작할 이유가 없어 URP 로 정했다.

버전을 `6000.3.21f1` 로 고정한 이유는, 상위 버전으로 열면 프로젝트가 자동
업그레이드되어 되돌리기 어렵고 `ProjectVersion.txt` 가 계속 충돌하기 때문이다.

## 2026-08-05 · 웹 네이티브 대신 Unity 선택

처음에는 웹 네이티브(Babylon.js 등)를 권했다. 근거는 "Unity 는 AI 가 닿는 면적이
좁다" 였다. 씬 배치와 인스펙터 조작은 사람이 에디터에서 해야 하므로, AI 활용도가
심사 대상인 과제에서 불리하다고 봤다.

**Unity MCP** 로 씬·GameObject·컴포넌트·프리팹까지 조작할 수 있다는 점을 확인하고
그 근거를 접었다. 여기에 팀 3인이 전원 Unreal 경험자라는 점이 결정적이었다.
Unreal → Unity 는 에디터·씬·컴포넌트 개념이 전이되지만, 웹 네이티브는 에디터가
없는 완전히 다른 패러다임이다.

남은 단점은 WebGL 빌드 시간이다. 에디터 플레이 모드로 개발하고 배포 시점에만
빌드하는 방식으로 완화한다.

버린 안: 웹 네이티브(팀 역량 리스크), Unreal(웹 빌드 불가, APK 전용)
