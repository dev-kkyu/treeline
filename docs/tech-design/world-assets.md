## 표면 — 절차적 생성

`docs/world-textures/gen_textures.py` 가 17종을 만든다. **주기 함수로 만들기 때문에
타일링이 수학적으로 보장된다** — 격자 인덱스를 주기로 나눈 나머지로 감기므로 좌우 ·
상하 끝이 일치한다.

| 표면 | 쓰이는 곳 |
| --- | --- |
| `concrete_wall` | 1 · 2장 벽 — 겉넓이의 절반을 덮는다 |
| `concrete_floor` | **젖은** 변주. 물이 있을 곳에만 쓴다 |
| `concrete_floor_dry` | **1장 실내 바닥.** 젖은 것을 깔았더니 관제동이 물바다로 보였다 |
| `steel_panel` | 넓은 실내 벽. 이음매를 지오메트리 없이 얻는다 |
| `painted_steel` · `rusted_steel` | 전 장 트림 · 배관 |
| `metal_grating` | 5장 철탑 · 6장 승강장 |
| `rock_hewn` | **3장** 갱도 벽 · 천장 — 파낸 곳이라 콘크리트를 쓰지 않는다 |
| `fuel_pool` | **3장** 바닥에 고인 연료. 쏘면 불바다가 되는 그 자리 |
| `scorched` | **3장** 태우고 지나간 구간. 두 번째 통과를 다르게 만든다 |
| `nest` · `nest_floor` · `nest_fiber` | **4장** 벽·천장 / 바닥 / 기둥·배관을 감는 것 |
| `snow` | 5장 손 안 탄 눈 |
| `snow_packed` | **5장** 걷는 자리. 발밑이 읽혀야 하는 곳 |
| `galvanized` | **5장** 철탑 · 6장 삭도 구조물 |
| `rime_ice` | **5장** 착빙 · 6장 케이블 |

```bash
python docs/world-textures/gen_textures.py --size 512          # 전체
python docs/world-textures/gen_textures.py --only nest snow    # 일부
python docs/world-textures/seam_check.py <폴더> --tile         # 이음매 검사
```

출력은 `Treeline/Assets/Game/World/Textures/` 에 albedo · normal · mask 세 장씩
떨어진다. mask 는 URP 규약대로 **R = metallic, A = smoothness** 다.

**512px 로 통일한다.** 1024 로 뽑으면 4종만으로 27 MB 였고, 512 로 내려도 손전등
거리에서 차이가 보이지 않았다.

실측 — 15종 45장이 **파일 7.01 MB · Unity 안에서 15.35 MB** 였다. 한 종을 더해도
1 MB 남짓이라 종수를 아끼는 것보다 **장에 맞는 표면을 갖추는 쪽이 이득**이다.

> 정정: 이 자리에 「7종 12.4 MB」로 적혀 있었는데 실측과 맞지 않았다. 같은 커밋의
> 텍스처를 다시 재보니 21장에 파일 3.21 MB 였다. 아래 `Crawler` 비교의 10.67 MB 는
> **Unity 안에서의 크기**가 맞다(다시 재서 확인). 두 수치의 잣대가 섞여 있었다.

### 노이즈 종류를 형태에 맞춘다

| 형태 | 방법 |
| --- | --- |
| 콘크리트 · 금속 | value 노이즈 (fBm) |
| **유기적인 것** (둥지의 살 · 암반 덩어리) | **셀룰러(Worley)** — value 노이즈는 뭉게구름이라 막(膜)이 안 나온다 |
| **규칙적인 무늬** (그레이팅 격자) | **도형으로 그린다** — 노이즈로는 안 나온다 |
| **방향이 있는 것** (흘러내린 물 · 바람이 쓴 눈 · 섬유 결) | **`stretch()`** — 등방 노이즈를 한 축으로만 뭉갠다 |

방향이 있는 무늬가 필요한 이유는 자연의 무늬가 대개 **한 방향으로 작용한 힘**에서
나오기 때문이다. 물은 아래로 흐르고 바람은 한쪽으로 분다. fbm 과 worley 는 등방이라
이것만으로는 못 만든다.

IMPORTANT: **셀룰러를 한 겹만 쓰면 「점무늬」가 된다.** 격자 한 칸에 특징점이 하나씩
들어가 셀 크기가 거의 같아지기 때문이다. 렌더해 보고서야 알았다 — 둥지가 붉은
물방울무늬로, 다져진 눈이 **눈에 핀 파란 곰팡이**로 보였다. `cellular()` 로 여러 겹
쌓으면 큰 셀 안이 작은 셀로 갈려서 크기가 흐트러진다.

그리고 눈에는 애초에 셀이 없다. `snow_packed` 는 셀룰러를 통째로 걷어내고 바람 결
하나로 다시 만들었다. **노이즈 종류는 취향이 아니라 형태가 정한다.**

### 이 게임의 조명에서는 알베도 색이 화면에 거의 안 나온다

IMPORTANT: 둥지 알베도는 텍스처 자체의 R/G 가 3.0 인데 화면에서는 회색으로
나왔다. 텍스처를 잘못 만든 줄 알고 두 번 고쳤는데, **중성 회색인 콘크리트도 같은
색으로 나왔다.**

| 천장 영역 | R/B | R/G |
| --- | --- | --- |
| 콘크리트 (중성 회색) | 0.80 | 0.90 |
| 둥지 (텍스처 R/G = 3.0) | 0.83 | 0.94 |

안개와 환경광의 푸른색이 화면 색을 정한다. 손전등을 올리면 그제야 붉은기가 나온다.

**레벨을 만들 때 색으로 구분하려 하면 안 된다. 명도와 형태로 구분한다.**

#### 다만 조명이 세지면 색이 돌아온다 (2026-08-09 · 4장)

위 규칙에는 조건이 하나 붙는다 — **어두울 때** 그렇다는 것이다. 4장에서 전력이
복구되어 천장 조명 아홉이 켜지자 **홀 전체가 붉게 물들었다.** 같은 `W_nest` 이고
텍스처도 그대로인데, 빛이 세지니 알베도가 화면을 지배했다.

이건 사고가 아니라 이 장이 노리던 것이다. 기획의 「어둠이 걷히면서 오히려 더
무서워지는 구간」이 **공짜로 나왔다.** 손전등만 들고 다닐 때는 회색 콘크리트로
보이던 벽이, 불이 들어오는 순간 살로 보인다.

그래서 규칙을 이렇게 고쳐 적는다. **손전등과 소형 광원만 있는 구간에서는 색으로
구분하지 말고, 밝히는 연출이 붙는 구간에서는 색이 곧 연출이다.**

IMPORTANT: 아래 「밝은 조명에서는 노멀이 사라지고 알베도만 남는다」와 **같은
현상을 반대쪽에서 본 것이다.** 4장을 지은 세션은 화면이 붉어지는 것을 봤고,
표면을 잰 세션은 결이 사라지는 것을 봤다. 원인이 하나다 — 밝은 빛 아래서는
화면을 정하는 것이 노멀이 만드는 그늘이 아니라 알베도다.

### 밝은 조명에서는 노멀이 사라지고 알베도만 남는다

IMPORTANT: 위 항목의 **정확한 뒤집힘**이다. 1 · 2 · 6장은 손전등뿐이라 처음 7종을
전부 그 조건에서만 조율했는데, **4장은 마지막에 전력이 들어오고 5장은 대낮이다.**
그 두 장에 놓기 전에 재봤더니 표면이 통째로 밋밋해졌다.

같은 판을 세 조명에서 렌더하고 「결이 얼마나 남는가」(화면 표준편차 ÷ 밝기)를 쟀다.

| 표면 | 손전등 | 조명 켜짐 (4장) | 밤 눈보라 (5장) | 알베도 대비 |
| --- | --- | --- | --- | --- |
| `metal_grating` | 0.392 | 0.299 | **0.261** | 0.863 |
| `rusted_steel` | 0.249 | 0.158 | 0.142 | 0.095 |
| `concrete_wall` | 0.271 | 0.111 | **0.034** | 0.043 |
| `painted_steel` | 0.254 | 0.115 | **0.033** | 0.033 |
| `snow` | 0.262 | 0.094 | **0.017** | 0.020 |

IMPORTANT: 5장 열은 처음에 **대낮으로 재고 적었다.** 2026-08-09 에 5장을 **밤**으로
정하고 다시 쟀는데 순위도 크기도 거의 같았다 — 달빛(0.50)과 눈이 되돌리는 환경광
(0.26)이 낮보다 약해도 **노멀의 그늘을 채우기에는 충분**하기 때문이다. 그래서
**표면 여덟 종은 다시 만들지 않았다.**

순위가 **알베도 대비와 정확히 일치한다.** 이유는 간단하다 — 노멀이 만드는 것은
그늘인데, 밝은 환경광은 사방에서 오므로 그 그늘을 서로 채워 지운다. 그늘이 지워져도
남는 것은 표면 자체의 명암, 즉 알베도뿐이다. 그레이팅만 버틴 것도 그것이 유일하게
**노이즈가 아니라 도형으로 그려진** 표면이어서다.

**밝은 곳에 놓을 표면은 노멀에 기대면 안 된다.** 4 · 5장용으로 새로 만든 것은 전부
알베도 대비를 0.09 이상으로 잡았고, 둥지는 색을 두 점에서 세 점으로 늘려
0.133 → 0.263 으로 올렸다. 4장의 「조명이 켜지는 순간」이 이 장의 핵심이라
그때 살덩이가 붉은 판때기로 보이면 안 된다.

여기서 「밝은 곳」은 **낮이라는 뜻이 아니다.** 환경광이 사방에서 오는 곳이라는 뜻이고,
5장은 밤인데도 눈이 달빛을 되돌려 그 조건이 된다. 실제로 밤 눈보라에서 재도
`concrete_wall` 이 0.271 → 0.034 로 무너진다.

눈은 예외로 둔다. 알베도 대비 0.020 은 **물리적으로 맞고**, 기획도 5장을
「하얘서 안 보인다」로 두었다. 다만 발밑까지 안 보이면 게임이 안 되므로 걷는
자리에는 `snow_packed`(0.092)를 깔아 지면이 읽히게 한다.

## 모델 — Meshy 생성 후 후처리

절차는 [`/prop` 스킬](../../.claude/skills/prop/SKILL.md) 에 있다. 요약하면
**목록 → 프롬프트 → Meshy → 임포트 후처리** 이고, 앞의 둘은 세션이, Meshy 는
사람이, 마지막은 MCP 가 한다.

적과 달리 **모델링 시트를 만들지 않는다.** 시트가 필요했던 이유는 적 3종의
실루엣 구분이 기획의 검수 기준이었기 때문이고, 레버 · 밸브 · 계기판은 서로
헷갈릴 일이 없다.

### 후처리 기준

모델이 올 때마다 감으로 하지 않도록 값을 고정한다. 근거는 `Crawler` 실측이다 —
Meshy 기본값이 2048px 3 장이라 **적 한 마리가 10.67 MB** 로, 월드 표면 **15 종
45 장(15.35 MB)** 의 3분의 2 에 이른다. 둘 다 Unity 안에서의 크기다.

| 항목 | 기준 |
| --- | --- |
| 텍스처 해상도 상한 | **1024** (소품은 512) |
| albedo sRGB | 켠다 |
| normal | `TextureImporterType.NormalMap` |
| mask · roughness · AO | sRGB **끈다** (색이 아니라 데이터) |
| 축 | 앞 `+Z`, 위 `+Y` |
| 피벗 | 손에 들리는 것은 손잡이, 놓이는 것은 바닥 중앙 |
| 콜라이더 | 박스. 메시 콜라이더는 쓰지 않는다 |

### 고치기 비싼 것은 입구에서 막는다

**Unity 안에서는 형태 · 폴리곤 · UV 를 고칠 수 없다.** ProBuilder 변환이 막혀 있고
MCP 로는 정점을 의미 있게 편집하지 못한다.

IMPORTANT: 팀에는 **Blender 경로가 살아 있다.** `Crawler` 리깅과 2장 복도
(`Ch2_CorridorSection.fbx`)가 그것으로 만들어졌다. 그러니 「절대 못 고친다」가
아니라 **「고치려면 Blender 를 쓸 사람이 필요하다」** 가 맞다. 프롬프트로 막으면
그 왕복이 없어진다.

그래서 프롬프트에 아래를 반드시 넣는다.

- `low-poly, game-ready, clean topology`
- `no baked shadows, no baked ambient occlusion` — 알베도에 그림자가 구워지면
  손전등과 싸운다
- 시대 · 국적을 특정하는 요소 제외

### 각진 물건은 Unity 에서 조합해도 된다

**대안이지 기본값이 아니다.** 팀은 Meshy 로 가기로 정했고, 이 경로는 Meshy 가
막히거나(키 · 쿼터 · 품질) 급할 때의 선택지로 남긴다.

R&D 에서 확인한 것 — 원통과 상자를 조합해 만들고 `Mesh.CombineMeshes` 로 구우면
**단일 메시 에셋**이 된다. 하드서페이스 제작의 표준 방식이다.

| | 조합 제작 (손전등) | Meshy (Crawler) |
| --- | --- | --- |
| 삼각형 | 812 | 10,960 |
| 텍스처 용량 | 0 (기존 머티리얼 재사용) | 10.67 MB |
| 같은 결과 | 항상 | 매번 다르다 |
| 마음에 안 들 때 | 숫자를 바꿔 다시 굽는다 | 다시 뽑는다 |

한계도 있다 — 부품이 서로 파고들어 안 보이는 면이 남고, 부품 간 부드러운 셰이딩이
안 되며, Unity 기본 원통이라 분할이 고정이다. 어둡고 저폴리가 유리한 이 게임에서는
셋 다 문제되지 않았다.

### 리깅이 필요한 것은 생각보다 적다

1 인칭 무기가 요구하는 움직임을 나누면 이렇다.

| 동작 | 필요한 것 |
| --- | --- |
| 반동 · 흔들림 · 들기 · 내리기 | 트랜스폼 |
| 슬라이드 후퇴 · 탄창 배출 | 트랜스폼 (**부품을 나눠 두면**) |
| 손가락이 탄창을 쥐는 것 | 리깅 |

**손을 화면에 보여주지 않기로 하면 리깅이 통째로 사라진다.** 움직일 부품이 있는
모델은 Meshy 에서 **나눠 뽑거나** 조합 제작으로 간다. 통짜로 오면 못 나눈다.

## UV — 스케일한 큐브는 텍스처가 늘어난다

기본 큐브의 UV 는 면마다 0~1 이라, 4m 로 늘리면 텍스처도 같이 늘어난다. 텍스처가
없을 때는 안 보이던 문제이고 **표면을 입히는 순간 드러난다.**

콘크리트는 「좀 뭉갰네」로 넘어가지만 **그레이팅 같은 규칙적 무늬는 줄무늬로 풀려
무엇인지 알 수 없게 된다.**

해법은 오브젝트 크기에서 타일링을 계산해 `MaterialPropertyBlock` 으로 넣는 것이다.
지오메트리를 건드리지 않고, 프리팹도 머티리얼도 갈라지지 않는다.

```csharp
var mpb = new MaterialPropertyBlock();
r.GetPropertyBlock(mpb);
mpb.SetVector("_BaseMap_ST", new Vector4(size.x * perMeter, size.z * perMeter, 0, 0));
r.SetPropertyBlock(mpb);
```

`perMeter` 는 재질마다 다르다 — 그레이팅은 0.78 (셀 하나 ≈ 0.16m), 콘크리트 · 눈은
0.5 (텍스처가 2m 를 덮음) 를 썼다.

IMPORTANT: 이것은 **축 정렬된 상자에만 통한다.** 모서리를 깎거나 면을 뚫으면 새로
생긴 면의 UV 를 못 맞춘다. 그때는 ProBuilder 가 필요하다.

### 컴포넌트로 들어갔다 — `World/SurfaceTiling.cs`

붙이면 크기에서 계산해 넣는다. `includeChildren` 을 켜면 자식이 각자 크기로 받으므로
**벽 수십 개에 하나씩 붙이지 않아도 된다.** 1장은 `Building` 루트에 하나만 붙였다.

R&D 예제가 안 다룬 것이 하나 있었다. **`_BaseMap_ST` 는 여섯 면에 똑같이 적용된다.**
바닥은 `x · z`, 동서 벽은 `x · y`, 남북 벽은 `z · y` 를 써야 하는데 셋을 동시에 맞출
수 없다. 예제의 `(size.x, size.z)` 는 바닥 기준이라 **벽에 그대로 쓰면 세로가
어긋난다.** 우리 회색 박스는 전부 납작한 판이므로 **가장 얇은 축을 버리는** 것으로
자동 판정한다. 실제로 방향이 다른 두 벽(`14×4×1` 과 `1×4×14`)이 똑같이 `7.00 × 2.00`
으로 나온다. 안 맞는 자리는 `axes` 로 지정한다.

확인은 **그레이팅으로 했다.** 콘크리트는 차이가 미묘해서(같은 화면에서 픽셀 평균
0.0475) 눈으로 판정하기 어렵지만, 그레이팅은 보정 없이는 격자가 몇 칸으로 늘어나
무엇인지 알 수 없게 된다. 두 장을
[`world-textures/uv-check/`](../world-textures/uv-check/) 에 남겨 두었다.

IMPORTANT: `MaterialPropertyBlock` 을 쓰면 **그 렌더러는 SRP Batcher 경로에서
빠진다.** 지금 규모에서는 문제가 아니지만, 빌드가 무거워지면 여기를 먼저 본다.

## ProBuilder — 설치했으나 보류

`com.unity.probuilder` 6.1.2 를 설치했다. 필요할 때 쓰고, **지금 이것 때문에 무엇을
바꾸지 않는다.**

| 시도 | 결과 |
| --- | --- |
| `create_shape` · `bevel_edges` · `auto_smooth` · `set_face_uvs` | 동작한다 |
| **`convert_to_probuilder`** | **예외로 죽고, 못 쓰는 `ProBuilderMesh` 를 남긴다** |
| ProBuilderize 메뉴 호출 | 경로가 안 잡힌다 |

즉 **이미 놓인 큐브를 변환할 수 없다.** 새로 만드는 것만 된다. 그리고 베벨을 넣은
뒤 UV 와 셰이딩을 세 번 고쳤는데도 평범한 스케일 큐브만큼 나오지 않았다. 한 단계마다
손으로 다시 잡아야 하는 도구다.

IMPORTANT: **2장은 이미 다른 길로 갔다.** `Ch2_CorridorSection.fbx` 처럼 Blender 로
칸을 통째로 만들어 넣는 방식이고, 그쪽이 ProBuilder 보다 잘 돌아갔다. 형태를 깎아야
할 일이 생기면 ProBuilder 가 아니라 **Blender 경로**를 먼저 본다.

`create_shape` 는 `size` 를 배열 · 객체 둘 다 받지 못한다. `width` / `height` /
`depth` 스칼라를 쓴다.

### 모서리를 살리는 값싼 방법은 따로 있다

베벨로 얻으려던 것 — 모서리가 빛을 받아 테두리가 생기는 것 — 은 **얇은 상자를
덧대서** 이미 하고 있다. `CorridorKit` 의 걸레받이 · 레일 · 천장 리브가 그것이고,
R&D 복도에서도 그쪽이 더 잘 나왔다.

## 검사 — 「seamless」를 믿지 않는다

CC0 텍스처를 검토하다 발견했다. ambientCG 의 `Concrete031` 은 **원본 1K 에서 이미
세로 이음매가 있었다** (끝단 불연속이 내부의 3.7 배). 리사이즈 탓인 줄 알고 원본을
따로 재서 확인했다.

`seam_check.py` 가 후보를 걸러낸다. **다만 판정은 사람이 한다.**

자동 판별을 두 가지 시도했고 둘 다 실패했다. 기록해 둔다.

- **크기로 가르기** (내부 최대 불연속과 비교) — 광학 스캔은 내부에 균열이 있어
  진짜 이음매인 `Concrete031` 이 통과해 버렸다
- **주기성으로 가르기** — 역시 통과시켰다. **오탐보다 이쪽이 위험하다.** 멀쩡한
  것을 버리는 것보다 깨진 것을 들여보내는 쪽이 나쁘다

규칙적인 무늬는 정상인데도 걸린다. 그레이팅 노멀맵이 7.68 로 걸렸는데 내부 살
경계와 비교하니 1.00 이었다. `--tile` 로 2x2 그림을 내주므로 네 귀퉁이가 만나는
자리만 보면 된다.

**끝단 절댓값을 같이 낸다.** 비율이 높아도 절댓값이 8비트 한 계단(1.0)에 못 미치면
`잡음` 으로 표시하고 넘어간다 — 표현할 수 없는 값에는 이음매가 담길 수 없다. 이건
위의 실패한 자동 판별 둘과 다르다. 그쪽은 「이 정도면 무늬겠지」라는 추측이었고,
이건 산수다. 실제로 `fuel_pool` 이 비율 1.87 로 걸렸는데 끝단이 0.19 계단이었다.
거의 평평한 노멀맵이라 분모가 0 에 가까워 나온 수치였다.

## 눈보라 — 5장

부품은 이미 있다. `VFX/Prefabs/PS_Blizzard`(World 공간 · 900입자 · Stretch 빌보드),
`Levels/SnowGusts.cs`(두 주기를 겹쳐 강약), 소리 두 종(`blizzard-outside-loop` ·
`blizzard-muffled-loop`). B 가 타이틀 · 엔딩용으로 만든 것을 5장이 받는다.

**타이틀과 5장의 차이는 「보는 화면」과 「걷는 화면」이다.** 이미터는 카메라에
붙이되 `simulationSpace` 는 **World 로 둔다.** 그래야 플레이어가 움직여도 눈이
끌려오지 않고 제 속도로 흩날린다. 이 구조는 프리팹에 이미 맞게 되어 있다.

### 값은 컴포넌트와 프리팹에 굳혀 두었다

문서에만 적어 두면 5장을 지을 때 손으로 다시 넣어야 한다. 그래서 두 가지를 만들었다.

| 무엇 | 어디 | 하는 일 |
| --- | --- | --- |
| `Levels/Whiteout.cs` | 컴포넌트 | 안개 · 하늘 · 눈발 바탕값을 한 자리에서 잡는다 |
| `VFX/Prefabs/Blizzard_Whiteout` | 프리팹 | 눈발 + 강약(`SnowGusts`) + 바람소리 + 위 컴포넌트 |

**쓰는 법은 프리팹을 카메라 밑에 떨어뜨리는 것 하나다.** 되돌린 씬에 그것만 하고
렌더해 검증했다 — 안개 0.089, 카메라 단색, 스카이박스 없음, 화면 점유 46%.

`Whiteout` 이 받는 값은 밀도가 아니라 **보이는 거리(m)** 다. `1.517 / 거리` 로
환산하므로 「17m 앞이 안 보인다」를 그대로 넣으면 된다. 안개색과 하늘색은 **한
필드**로 묶었다 — 둘이 다르면 지평선이 선으로 남기 때문에 갈라 둘 이유가 없다.

IMPORTANT: 눈발 값은 **편집 중에만** 씬에 쓴다. `SnowGusts` 가 `Awake` 에서 발생
수를 읽어 「바탕」으로 삼는데, 같은 프레임에 양쪽이 `Awake` 에서 쓰면 순서가 정해져
있지 않다. 편집 중에 넣어 씬에 저장하면 그 경합이 사라진다.

`World/_RnD_Blizzard.unity` 에 검증한 구성을 남겨 두었다.

### 시야 거리는 파티클이 아니라 안개가 만든다

기획의 「시야가 몇 미터」를 파티클로 만들려 하면 안 된다. 먼 것을 가리려면 수만 개가
필요하고 WebGL 이 죽는다. 가리는 일은 안개가 하고, 파티클은 **가까이에서 흩날리는
것**만 맡는다.

`ExponentialSquared` 에서 90% 가려지는 거리는 `1.517 / density` 다.

| density | 90% 가려지는 거리 |
| --- | --- |
| 0.05 | 30 m |
| **0.09** | **17 m** |
| 0.14 | 11 m |

**0.09 로 잡았다.** 유도등 간격을 15~20 m 로 두면 「하나를 켜면 다음 것이 흐릿하게
보인다」가 그대로 나온다. 밤으로 바꿔도 이 값은 그대로다 — 가리는 거리를 정하는 것은
안개 밀도이고 밝기와 무관하다.

### 하늘을 `Skybox/Procedural` 로 만들면 안 된다

IMPORTANT: 두 번 실패했다.

- `M_Ch1_Blizzard_Sky`(B 가 1장 창밖용으로 만든 것)를 그대로 썼더니 **노을이 됐다.**
  이 셰이더는 태양 방향으로 색을 계산한다. 1장은 창으로 조금만 보여서 괜찮았지만
  5장은 하늘이 화면의 절반이다
- `AtmosphereThickness` 를 0 으로 내려 단색을 만들려 했더니 **검은 하늘**이 됐다.
  산란 계산이 통째로 죽는다 (`W_sky_black` 이 정확히 그 방법이다)

**카메라를 `SolidColor` 로 지우고 안개색과 같은 색을 넣는다.** 하늘과 안개가 정확히
같은 색이어야 지평선이 사라지고, 기획의 「위아래도 잘 구분되지 않는다」가 된다.
스카이박스를 안 그리므로 WebGL 에서도 가장 싸다.

### 밤이다 — 달빛이 눈에 되돌아 하얘진다

IMPORTANT: 5장은 **밤**이다. 2026-08-09 에 팀이 정했다. 이 게임은 모든 장이 어둡고
5장도 예외가 아니며, 화면이 하얀 것은 낮이라서가 아니라 **달빛이 눈과 눈보라에
무수히 산란해 되돌아오기 때문**이다.

6장도 밤이라 시각이 이어진다. 그런데 6장(안개 0.06 · 0.08 · 0.10)보다 5장이 두 배쯤
밝은 것은 모순이 아니다 — **같은 밤인데 5장은 탁 트인 눈밭이고 눈보라가 한창이라
빛을 되돌리는 것이 훨씬 많다.** 6장은 승강장이라 구조물이 하늘을 가리고 눈보라도
잦아들었다.

세 밝기를 나란히 찍어 골랐다.

| | 공기색 | 환경광 | 달빛 | 화면 밝기 |
| --- | --- | --- | --- | --- |
| 6장 (참고) | 0.06 · 0.08 · 0.10 | 0.115 · 0.145 · 0.190 | 0.20 | 0.176 |
| 옅은 밤 | 0.22 · 0.26 · 0.32 | 0.16 · 0.19 · 0.24 | 0.35 | 0.294 |
| **5장** | **0.34 · 0.38 · 0.46** | **0.26 · 0.30 · 0.36** | **0.50** | **0.394** |
| 밝은 밤 | 0.46 · 0.50 · 0.58 | 0.34 · 0.38 · 0.45 | 0.65 | 0.493 |

옅은 밤은 지평선이 아직 선으로 남고, 밝은 밤은 철탑 실루엣까지 흐려진다.

### 눈발 색은 배경보다 어두울지 밝을지로 정한다

배경보다 **얼마나 벗어나는가**가 눈발이 보이는 정도를 정한다. 그래서 눈발 색은
고정값이 아니라 **배경 밝기에 따라 뒤집힌다.**

| 배경 | 흰 눈발 | 회색 눈발 |
| --- | --- | --- |
| **밤 눈보라 0.377 (5장)** | **27.2%** | 18.1% |
| 대낮 0.827 (버린 가정) | 36.4% | **46.2%** |

**밤에는 흰 것이 맞다.** 낮으로 가정했을 때 만든 회색 눈발
(`MAT_SnowStreak_Whiteout`)은 그래서 지웠다. 6장처럼 더 어두운 곳에 쓸 때는 흰 것이
더 유리해진다.

크기가 색보다 센 지렛대인 것은 낮밤 공통이다. 발생 수를 1400 으로 고정하고 재면
크기 0.12 에서는 색을 바꿔도 거의 안 변하고(17.6% 대 16.1%) 0.26 에서야 갈린다 —
입자가 작으면 픽셀당 덮는 양이 적어 **안개가 그 색을 배경색으로 끌어당긴다.**
안개를 끄고 재면 편차가 0.167 → 0.535 로 뛰어 그것이 안개 탓임이 확인된다.

밀도는 셋 중 가장 약하다. 420 → 1400 으로 3.3 배 올려도 크기 0.12 에서는 몇 %p 다.
박스 깊이는 거의 영향이 없었다(10 m → 4 m 에 1%p).

권장값은 `startSize 0.26` · `rateOverTime 1400` · **흰 눈발**(`MAT_SnowStreak`) 이고
프리팹에 굳혀 두었다.

> 정정 둘. 처음에 「색은 지렛대가 아니다」로 적었는데 **크기 0.12 에서만 재고 낸
> 결론**이었다. 그다음엔 회색이 답이라고 적었는데 그것은 **5장을 대낮으로 가정한
> 위에서만 참**이었다. 두 번 다 조건을 좁게 잡고 결론을 넓게 적은 것이다.

IMPORTANT: **화면 점유 58% 의 WebGL 부하는 아직 안 쟀다.** 반투명이 화면의 절반을
덮으므로 오버드로가 이 게임에서 가장 비싼 자리가 될 수 있다. 5장을 지을 때 실기에서
프레임을 재고, 무거우면 **크기를 줄이는 대신 안개를 올려** 같은 인상을 만든다.

### 5장에서는 어두운 것이 보인다

1~4장은 어둠 속에서 **빛을 받은 것**이 보였다. 5장은 뒤집힌다 — 배경이 밝으므로
**배경보다 어두운 것만** 실루엣으로 선다. 기획의 「하얀 눈보라, 실루엣들」이 그것이다.

밤으로 바꿔도 이 관계는 그대로다. 밤 눈보라에서 눈이 0.416, `galvanized` 철탑이
0.245 로 **59%** 라 실루엣이 선다(대낮 가정에서는 0.785 대 0.409 로 52% 였다).
적도 같은 이유로 어두워야 한다.

유도등은 반대다. 광원은 안개를 못 뚫으므로 **가산 합성 발광 카드**를 같이 세운다
(`VFX/Materials/MAT_GuideGlow`, `soft-disc.png`). 카드를 붙인 뒤 45 m 유도등이
주변보다 6% 밝아져 화면에 남았다.

## 어두운 게임의 이점

배경이 어두우면 **에셋 품질 요구가 크게 낮아진다.** 텍스처 디테일과 폴리곤이
보이지 않고 조명과 실루엣이 인상을 결정한다. 서로 다른 출처를 섞을 때 이질감이 가장
적게 드러나는 조건이기도 하다. 먼 거리를 안 그려도 되므로 WebGL 부담도 준다.

기획이 이것을 이점으로 명시했고, R&D 가 그것을 확인했다.
