## 표면 — 절차적 생성

`docs/world-textures/gen_textures.py` 가 7종을 만든다. **주기 함수로 만들기 때문에
타일링이 수학적으로 보장된다** — 격자 인덱스를 주기로 나눈 나머지로 감기므로 좌우 ·
상하 끝이 일치한다.

| 표면 | 쓰이는 곳 |
| --- | --- |
| `concrete_wall` · `concrete_floor` | 1 · 2 · 3장 |
| `painted_steel` · `rusted_steel` | 전 장 트림 · 배관 |
| `metal_grating` | 5장 철탑 · 6장 승강장 |
| `nest` | 4장 발전동 |
| `snow` | 5장 눈보라 |

```bash
python docs/world-textures/gen_textures.py --size 512          # 전체
python docs/world-textures/gen_textures.py --only nest snow    # 일부
python docs/world-textures/seam_check.py <폴더> --tile         # 이음매 검사
```

출력은 `Treeline/Assets/Game/World/Textures/` 에 albedo · normal · mask 세 장씩
떨어진다. mask 는 URP 규약대로 **R = metallic, A = smoothness** 다.

**512px 로 통일한다.** 1024 로 뽑으면 4종에 27 MB 인데 512 는 7종에 12.4 MB 다.
손전등 거리에서 차이가 보이지 않았다.

### 노이즈 종류를 형태에 맞춘다

| 형태 | 방법 |
| --- | --- |
| 콘크리트 · 금속 · 눈 | value 노이즈 (fBm) |
| **유기적인 것** (둥지의 살 · 섬유질) | **셀룰러(Worley) 노이즈** — value 노이즈는 뭉게구름이라 막(膜)이 안 나온다 |
| **규칙적인 무늬** (그레이팅 격자) | **도형으로 그린다** — 노이즈로는 안 나온다 |

### 이 게임의 조명에서는 알베도 색이 화면에 거의 안 나온다

IMPORTANT: 둥지 알베도는 텍스처 자체의 R/G 가 3.0 인데 화면에서는 회색으로
나왔다. 텍스처를 잘못 만든 줄 알고 두 번 고쳤는데, **중성 회색인 콘크리트도 같은
색으로 나왔다.**

| 천장 영역 | R/B | R/G |
| --- | --- | --- |
| 콘크리트 (중성 회색) | 0.80 | 0.90 |
| 둥지 (텍스처 R/G = 3.0) | 0.83 | 0.94 |

안개와 환경광의 푸른색이 화면 색을 정한다. 손전등을 올리면 그제야 붉은기가 나온다.

**레벨을 만들 때 색으로 구분하려 하면 안 된다. 명도와 형태로 구분한다.**

#### 다만 조명이 세지면 색이 돌아온다 (2026-08-09 · 4장)

위 규칙에는 조건이 하나 붙는다 — **어두울 때** 그렇다는 것이다. 4장에서 전력이
복구되어 천장 조명 아홉이 켜지자 **홀 전체가 붉게 물들었다.** 같은 `W_nest` 이고
텍스처도 그대로인데, 빛이 세지니 알베도가 화면을 지배했다.

이건 사고가 아니라 이 장이 노리던 것이다. 기획의 「어둠이 걷히면서 오히려 더
무서워지는 구간」이 **공짜로 나왔다.** 손전등만 들고 다닐 때는 회색 콘크리트로
보이던 벽이, 불이 들어오는 순간 살로 보인다.

그래서 규칙을 이렇게 고쳐 적는다. **손전등과 소형 광원만 있는 구간에서는 색으로
구분하지 말고, 밝히는 연출이 붙는 구간에서는 색이 곧 연출이다.**

## 모델 — Meshy 생성 후 후처리

절차는 [`/prop` 스킬](../../.claude/skills/prop/SKILL.md) 에 있다. 요약하면
**목록 → 프롬프트 → Meshy → 임포트 후처리** 이고, 앞의 둘은 세션이, Meshy 는
사람이, 마지막은 MCP 가 한다.

적과 달리 **모델링 시트를 만들지 않는다.** 시트가 필요했던 이유는 적 3종의
실루엣 구분이 기획의 검수 기준이었기 때문이고, 레버 · 밸브 · 계기판은 서로
헷갈릴 일이 없다.

### 후처리 기준

모델이 올 때마다 감으로 하지 않도록 값을 고정한다. 근거는 `Crawler` 실측이다 —
Meshy 기본값이 2048px 3 장이라 **적 한 마리가 10.67 MB** 로 월드 표면 7 종
(12.4 MB) 과 맞먹었다.

| 항목 | 기준 |
| --- | --- |
| 텍스처 해상도 상한 | **1024** (소품은 512) |
| albedo sRGB | 켠다 |
| normal | `TextureImporterType.NormalMap` |
| mask · roughness · AO | sRGB **끈다** (색이 아니라 데이터) |
| 축 | 앞 `+Z`, 위 `+Y` |
| 피벗 | 손에 들리는 것은 손잡이, 놓이는 것은 바닥 중앙 |
| 콜라이더 | 박스. 메시 콜라이더는 쓰지 않는다 |

### 고치기 비싼 것은 입구에서 막는다

**Unity 안에서는 형태 · 폴리곤 · UV 를 고칠 수 없다.** ProBuilder 변환이 막혀 있고
MCP 로는 정점을 의미 있게 편집하지 못한다.

IMPORTANT: 팀에는 **Blender 경로가 살아 있다.** `Crawler` 리깅과 2장 복도
(`Ch2_CorridorSection.fbx`)가 그것으로 만들어졌다. 그러니 「절대 못 고친다」가
아니라 **「고치려면 Blender 를 쓸 사람이 필요하다」** 가 맞다. 프롬프트로 막으면
그 왕복이 없어진다.

그래서 프롬프트에 아래를 반드시 넣는다.

- `low-poly, game-ready, clean topology`
- `no baked shadows, no baked ambient occlusion` — 알베도에 그림자가 구워지면
  손전등과 싸운다
- 시대 · 국적을 특정하는 요소 제외

### 각진 물건은 Unity 에서 조합해도 된다

**대안이지 기본값이 아니다.** 팀은 Meshy 로 가기로 정했고, 이 경로는 Meshy 가
막히거나(키 · 쿼터 · 품질) 급할 때의 선택지로 남긴다.

R&D 에서 확인한 것 — 원통과 상자를 조합해 만들고 `Mesh.CombineMeshes` 로 구우면
**단일 메시 에셋**이 된다. 하드서페이스 제작의 표준 방식이다.

| | 조합 제작 (손전등) | Meshy (Crawler) |
| --- | --- | --- |
| 삼각형 | 812 | 10,960 |
| 텍스처 용량 | 0 (기존 머티리얼 재사용) | 10.67 MB |
| 같은 결과 | 항상 | 매번 다르다 |
| 마음에 안 들 때 | 숫자를 바꿔 다시 굽는다 | 다시 뽑는다 |

한계도 있다 — 부품이 서로 파고들어 안 보이는 면이 남고, 부품 간 부드러운 셰이딩이
안 되며, Unity 기본 원통이라 분할이 고정이다. 어둡고 저폴리가 유리한 이 게임에서는
셋 다 문제되지 않았다.

### 리깅이 필요한 것은 생각보다 적다

1 인칭 무기가 요구하는 움직임을 나누면 이렇다.

| 동작 | 필요한 것 |
| --- | --- |
| 반동 · 흔들림 · 들기 · 내리기 | 트랜스폼 |
| 슬라이드 후퇴 · 탄창 배출 | 트랜스폼 (**부품을 나눠 두면**) |
| 손가락이 탄창을 쥐는 것 | 리깅 |

**손을 화면에 보여주지 않기로 하면 리깅이 통째로 사라진다.** 움직일 부품이 있는
모델은 Meshy 에서 **나눠 뽑거나** 조합 제작으로 간다. 통짜로 오면 못 나눈다.

## UV — 스케일한 큐브는 텍스처가 늘어난다

기본 큐브의 UV 는 면마다 0~1 이라, 4m 로 늘리면 텍스처도 같이 늘어난다. 텍스처가
없을 때는 안 보이던 문제이고 **표면을 입히는 순간 드러난다.**

콘크리트는 「좀 뭉갰네」로 넘어가지만 **그레이팅 같은 규칙적 무늬는 줄무늬로 풀려
무엇인지 알 수 없게 된다.**

해법은 오브젝트 크기에서 타일링을 계산해 `MaterialPropertyBlock` 으로 넣는 것이다.
지오메트리를 건드리지 않고, 프리팹도 머티리얼도 갈라지지 않는다.

```csharp
var mpb = new MaterialPropertyBlock();
r.GetPropertyBlock(mpb);
mpb.SetVector("_BaseMap_ST", new Vector4(size.x * perMeter, size.z * perMeter, 0, 0));
r.SetPropertyBlock(mpb);
```

`perMeter` 는 재질마다 다르다 — 그레이팅은 0.78 (셀 하나 ≈ 0.16m), 콘크리트 · 눈은
0.5 (텍스처가 2m 를 덮음) 를 썼다.

IMPORTANT: 이것은 **축 정렬된 상자에만 통한다.** 모서리를 깎거나 면을 뚫으면 새로
생긴 면의 UV 를 못 맞춘다. 그때는 ProBuilder 가 필요하다.

### 컴포넌트로 들어갔다 — `World/SurfaceTiling.cs`

붙이면 크기에서 계산해 넣는다. `includeChildren` 을 켜면 자식이 각자 크기로 받으므로
**벽 수십 개에 하나씩 붙이지 않아도 된다.** 1장은 `Building` 루트에 하나만 붙였다.

R&D 예제가 안 다룬 것이 하나 있었다. **`_BaseMap_ST` 는 여섯 면에 똑같이 적용된다.**
바닥은 `x · z`, 동서 벽은 `x · y`, 남북 벽은 `z · y` 를 써야 하는데 셋을 동시에 맞출
수 없다. 예제의 `(size.x, size.z)` 는 바닥 기준이라 **벽에 그대로 쓰면 세로가
어긋난다.** 우리 회색 박스는 전부 납작한 판이므로 **가장 얇은 축을 버리는** 것으로
자동 판정한다. 실제로 방향이 다른 두 벽(`14×4×1` 과 `1×4×14`)이 똑같이 `7.00 × 2.00`
으로 나온다. 안 맞는 자리는 `axes` 로 지정한다.

확인은 **그레이팅으로 했다.** 콘크리트는 차이가 미묘해서(같은 화면에서 픽셀 평균
0.0475) 눈으로 판정하기 어렵지만, 그레이팅은 보정 없이는 격자가 몇 칸으로 늘어나
무엇인지 알 수 없게 된다. 두 장을
[`world-textures/uv-check/`](../world-textures/uv-check/) 에 남겨 두었다.

IMPORTANT: `MaterialPropertyBlock` 을 쓰면 **그 렌더러는 SRP Batcher 경로에서
빠진다.** 지금 규모에서는 문제가 아니지만, 빌드가 무거워지면 여기를 먼저 본다.

## ProBuilder — 설치했으나 보류

`com.unity.probuilder` 6.1.2 를 설치했다. 필요할 때 쓰고, **지금 이것 때문에 무엇을
바꾸지 않는다.**

| 시도 | 결과 |
| --- | --- |
| `create_shape` · `bevel_edges` · `auto_smooth` · `set_face_uvs` | 동작한다 |
| **`convert_to_probuilder`** | **예외로 죽고, 못 쓰는 `ProBuilderMesh` 를 남긴다** |
| ProBuilderize 메뉴 호출 | 경로가 안 잡힌다 |

즉 **이미 놓인 큐브를 변환할 수 없다.** 새로 만드는 것만 된다. 그리고 베벨을 넣은
뒤 UV 와 셰이딩을 세 번 고쳤는데도 평범한 스케일 큐브만큼 나오지 않았다. 한 단계마다
손으로 다시 잡아야 하는 도구다.

IMPORTANT: **2장은 이미 다른 길로 갔다.** `Ch2_CorridorSection.fbx` 처럼 Blender 로
칸을 통째로 만들어 넣는 방식이고, 그쪽이 ProBuilder 보다 잘 돌아갔다. 형태를 깎아야
할 일이 생기면 ProBuilder 가 아니라 **Blender 경로**를 먼저 본다.

`create_shape` 는 `size` 를 배열 · 객체 둘 다 받지 못한다. `width` / `height` /
`depth` 스칼라를 쓴다.

### 모서리를 살리는 값싼 방법은 따로 있다

베벨로 얻으려던 것 — 모서리가 빛을 받아 테두리가 생기는 것 — 은 **얇은 상자를
덧대서** 이미 하고 있다. `CorridorKit` 의 걸레받이 · 레일 · 천장 리브가 그것이고,
R&D 복도에서도 그쪽이 더 잘 나왔다.

## 검사 — 「seamless」를 믿지 않는다

CC0 텍스처를 검토하다 발견했다. ambientCG 의 `Concrete031` 은 **원본 1K 에서 이미
세로 이음매가 있었다** (끝단 불연속이 내부의 3.7 배). 리사이즈 탓인 줄 알고 원본을
따로 재서 확인했다.

`seam_check.py` 가 후보를 걸러낸다. **다만 판정은 사람이 한다.**

자동 판별을 두 가지 시도했고 둘 다 실패했다. 기록해 둔다.

- **크기로 가르기** (내부 최대 불연속과 비교) — 광학 스캔은 내부에 균열이 있어
  진짜 이음매인 `Concrete031` 이 통과해 버렸다
- **주기성으로 가르기** — 역시 통과시켰다. **오탐보다 이쪽이 위험하다.** 멀쩡한
  것을 버리는 것보다 깨진 것을 들여보내는 쪽이 나쁘다

규칙적인 무늬는 정상인데도 걸린다. 그레이팅 노멀맵이 7.68 로 걸렸는데 내부 살
경계와 비교하니 1.00 이었다. `--tile` 로 2x2 그림을 내주므로 네 귀퉁이가 만나는
자리만 보면 된다.

## 어두운 게임의 이점

배경이 어두우면 **에셋 품질 요구가 크게 낮아진다.** 텍스처 디테일과 폴리곤이
보이지 않고 조명과 실루엣이 인상을 결정한다. 서로 다른 출처를 섞을 때 이질감이 가장
적게 드러나는 조건이기도 하다. 먼 거리를 안 그려도 되므로 WebGL 부담도 준다.

기획이 이것을 이점으로 명시했고, R&D 가 그것을 확인했다.
